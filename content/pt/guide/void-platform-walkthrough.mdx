Configurar uma infraestrutura de deploy compartilhada é fácil de adiar — até o momento em que três desenvolvedores estão cada um publicando na própria conta da Cloudflare e ninguém consegue reverter o mesmo release. Um guia prático da Void Platform resolve isso ao transformar uma ambição vaga de "deveríamos fazer self-host" em um checklist ordenado. A seguir você encontra um guia prático da Void Platform que cobre o que a plataforma realmente é, quais credenciais reunir primeiro, como a instalação principal é sequenciada e quais serviços opcionais a maioria das equipes adiciona depois.

A maior parte da confusão em torno deste produto vem de uma única bifurcação no caminho: fazer deploy para você mesmo versus fazer deploy para uma equipe. Se você está publicando seu próprio app, faz o deploy diretamente na Cloudflare e nunca toca em uma instalação de plataforma. Se você é o administrador responsável por levantar a infraestrutura compartilhada, a plataforma passa a ser aquilo que você instala, mantém e entrega como uma URL. Tudo aqui parte do princípio de que você está nesse segundo grupo.

## O que uma Void Platform realmente faz

Uma plataforma Void permite que uma equipe faça deploy de aplicações em uma conta compartilhada da Cloudflare. Essa única frase carrega a maior parte do valor: em vez de cada desenvolvedor configurar sua própria conta, tokens e gateway, o administrador instala e mantém uma plataforma. Os desenvolvedores então apontam a Void CLI para a URL dela, fazem login por um método de login habilitado e fazem o deploy.

A plataforma não é um produto de hospedagem separado. Ambos os alvos de deploy usam as mesmas APIs de aplicação, então um app não precisa ser reescrito para migrar de um deploy direto na Cloudflare para uma plataforma de equipe. O que a plataforma acrescenta é acesso compartilhado mais histórico de deploys retido — duas coisas que importam enormemente quando mais de uma pessoa publica código.

| Papel | O que é responsabilidade dele | Onde ele trabalha |
| --- | --- | --- |
| Administrador | Instalar e manter a plataforma, habilitar métodos de login, configurar o domínio de e-mail compartilhado | Conta da Cloudflare + URL da plataforma |
| Desenvolvedor | Conectar a Void CLI, fazer login, fazer deploy dos apps | Void CLI → URL da plataforma |
| Criador solo | Publicar um único app sem plataforma alguma | A própria conta da Cloudflare |

Essa divisão importa porque define o seu trabalho. Durante a instalação você é o administrador, não um desenvolvedor. Sua métrica de sucesso não é "meu app está no ar" — é "um colega de equipe que eu nunca vi consegue se autenticar e fazer deploy sem me mandar mensagem".

## Pré-requisitos e credenciais para reunir primeiro

A forma mais rápida de travar um guia prático da Void Platform é descobrir no meio do caminho que falta um nível de plano ou uma permissão de conta. O [guia oficial de instalação da plataforma self-hosted da Void](https://void.cloud/guide/self-hosted-platform) separa isso em pré-requisitos e credenciais por um bom motivo: são decisões distintas, com responsáveis distintos.

Percorra a lista abaixo antes de encostar no instalador. Cada linha é algo que você deveria conseguir responder com um nome, não com um encolher de ombros.

| Pré-requisito | Por que importa | Decidir antes da instalação? |
| --- | --- | --- |
| Conta dedicada da Cloudflare para a plataforma | Todo app da equipe faz deploy nessa única conta compartilhada | Sim — nunca uma conta pessoal |
| Workers Paid na conta da plataforma | Necessário para Sandboxes gerenciados | Sim |
| Workers for Platforms + infraestrutura documentada | Necessário para uma plataforma de equipe | Sim |
| Pelo menos um método de login | Desenvolvedores só conseguem fazer login por um método habilitado | Sim |
| Domínio e zona de e-mail compartilhados | O e-mail permanece desativado até ambos serem configurados | Somente se você quiser e-mail |
| Credenciais e acesso à API | Necessários para instalar e para manter ao longo do tempo | Sim |

Dois desses itens costumam ser subestimados. O primeiro é a escolha da conta: migrar uma plataforma depois é muito mais doloroso do que escolher uma conta dedicada desde o início. O segundo é o método de login — ele não é um detalhe pós-instalação, é o portão pelo qual todo desenvolvedor passa.

## O passo a passo da Void Platform, etapa por etapa

A sequência abaixo segue os guias de instalação em ordem, dos pré-requisitos às credenciais e daí para a instalação principal. Trate cada etapa como um portão: não avance até que a coluna "concluído" seja genuinamente verdadeira.

| # | Etapa | Como é "concluído" |
| --- | --- | --- |
| 1 | Decidir entre deploy direto e plataforma compartilhada | Você confirmou que realmente precisa de uma plataforma |
| 2 | Concluir os pré-requisitos | Conta, nível de plano e infraestrutura confirmados |
| 3 | Reunir as credenciais | Acesso de instalação e manutenção em mãos |
| 4 | Instalar a plataforma principal | Sandboxes gerenciados e gateway de e-mail presentes |
| 5 | Configurar o domínio e a zona de e-mail compartilhados | Gateway de e-mail ativo (opcional, mas recomendado) |
| 6 | Habilitar um método de login | Desenvolvedores conseguem se autenticar com sucesso |
| 7 | Conectar a Void CLI à URL da plataforma | Um primeiro deploy de teste funciona de ponta a ponta |
| 8 | Planejar os serviços opcionais | Uma lista escrita do que você vai adicionar depois |

### Etapas 1–3: Escopo, pré-requisitos, credenciais

Comece anotando a resposta para uma pergunta direta: esta plataforma é para uma pessoa ou para uma equipe? Se for para uma pessoa, pare — faça o deploy diretamente na Cloudflare. Se for para uma equipe, a resposta te compromete com Workers for Platforms e com a infraestrutura documentada, então reserve orçamento para isso antes de agendar qualquer janela de instalação.

### Etapas 4–5: Instalar o núcleo e ativar o e-mail

A instalação principal inclui Sandboxes gerenciados e um gateway de e-mail. O e-mail não entra no ar sozinho; ele é ativado quando você configura um domínio e uma zona de e-mail compartilhados. Se o envio de e-mails transacionais pelos apps publicados faz parte do seu plano, trate isso como uma etapa obrigatória em vez de um extra, e valide com um envio real antes de convidar os desenvolvedores.

### Etapas 6–8: Autenticação, primeiro deploy e o roteiro

Habilite um método de login, entregue a URL da plataforma a um desenvolvedor piloto e peça que ele conecte a Void CLI e faça o deploy de algo pequeno. Esse único teste revela mais problemas de configuração do que qualquer checklist. Depois que ele passar, anote os serviços opcionais que você está adiando — builds do GitHub, Build Containers, domínios de projeto personalizados — para que ninguém presuma que eles vieram junto com o núcleo.

## Cloudflare direto vs. a plataforma self-hosted principal

Esta é a tabela comparativa que vale salvar nos favoritos, porque responde "o que eu realmente ganho com isso?". Ambos os alvos compartilham as mesmas APIs de aplicação; as diferenças estão em acesso compartilhado, retenção e por onde as requisições passam.

| Recurso | Cloudflare direto | Plataforma self-hosted principal |
| --- | --- | --- |
| Workers AI e requisições a provedores | Sua conta e seu gateway | Gateway e proxy da instalação |
| Logs de runtime | Tail ao vivo da Cloudflare | Logs retidos na plataforma |
| Rollback de aplicação | Versões do Worker | Deploys retidos na plataforma |
| Sandboxes | Exige Workers Paid e Docker | Exige Workers Paid na conta da plataforma |
| Dashboard de usuário e builds gerenciados do GitHub | Não necessários | Não incluídos em uma instalação padrão |

Leia as duas últimas linhas com atenção. Sandboxes na plataforma só exigem Workers Paid na conta da plataforma, enquanto o deploy direto também espera Docker no seu fluxo local. E o dashboard mais os builds gerenciados do GitHub não fazem parte de uma instalação padrão em nenhum dos dois lados — são adições que você opta por fazer.

Para um projeto solo, a coluna da esquerda dá menos trabalho para as mesmas APIs de aplicação. Para uma equipe, os logs retidos e os deploys retidos da coluna da direita são o que torna possível depurar um release compartilhado.

## Serviços opcionais e armadilhas de configuração

Depois que o seu guia prático da Void Platform conclui a instalação principal, o trabalho restante é eletivo — mas cada opção tem uma consequência de configuração. Planeje-as deliberadamente em vez de descobri-las quando um desenvolvedor perguntar por que o preview da branch dele está faltando.

| Capacidade | Está na instalação principal? | O que saber |
| --- | --- | --- |
| Sandboxes gerenciados | Sim | Recurso principal |
| Gateway de e-mail | Sim, depois que o domínio e a zona de e-mail estiverem definidos | Desativado por padrão até ser configurado |
| Dashboard de usuário | Não | Adição opcional |
| Builds e webhooks do GitHub | Não | Opcional; plataformas construídas a partir do código-fonte que os adicionam devem usar a configuração de ingresso isolado de webhooks quando o Access protege a API |
| Build Containers | Não | Adição opcional |
| Domínios de projeto personalizados | Não | Adição opcional |

| Sintoma | Causa provável | Onde olhar |
| --- | --- | --- |
| Um desenvolvedor não consegue fazer login | Nenhum método de login habilitado | Configuração de login da plataforma |
| O e-mail nunca chega | Domínio e zona de e-mail compartilhados não configurados | Configuração do gateway de e-mail |
| Entregas de webhook falham atrás do Access | Ingresso não isolado | Configuração de ingresso isolado de webhooks |
| Sem histórico de rollback para um release | Deploy direto, não pela plataforma | Escolha do alvo de deploy |
| Recurso que você esperava está faltando | É um serviço opcional, não principal | Sua lista de serviços adiados |

Dois hábitos previnem a maioria desses casos. Primeiro, mantenha um registro curto de configuração: quais métodos de login estão habilitados, qual domínio de e-mail é compartilhado e quais serviços opcionais estão ativos. Segundo, quando o Cloudflare Access protege a API e você roda uma plataforma construída a partir do código-fonte com serviços do GitHub, siga a configuração de ingresso isolado de webhooks em vez de afrouxar o Access — a correção pertence ao caminho de ingresso, não à sua postura de segurança.

Por fim, lembre-se de que uma plataforma de equipe depende da configuração dela. Recursos documentados para uma instalação podem estar ausentes na sua simplesmente porque não foram habilitados, então verifique com base na sua própria configuração em vez de presumir um padrão.

## Perguntas frequentes

**Preciso de um guia prático da Void Platform se estou apenas fazendo deploy do meu próprio app?**
Não. Se você está fazendo deploy de um app para si mesmo, faça o deploy diretamente na Cloudflare. Instalar uma plataforma só compensa a sobrecarga quando uma equipe precisa de acesso compartilhado e histórico de deploys retido.

**O dashboard de usuário está incluído em uma instalação padrão?**
Não. O dashboard de usuário, os builds e webhooks gerenciados do GitHub, os Build Containers e os domínios de projeto personalizados não fazem parte da instalação principal. Planeje-os como adições separadas.

**O que a conta da plataforma precisa para rodar Sandboxes?**
Workers Paid na conta da plataforma. O deploy direto na Cloudflare tem um requisito um pouco diferente e também espera Docker para Sandboxes.

**Podemos adicionar builds do GitHub depois da instalação principal?**
Sim — é um serviço opcional. Se você está em uma plataforma construída a partir do código-fonte e o Cloudflare Access protege a API, configure o ingresso isolado de webhooks para que builds e webhooks continuem funcionando sem enfraquecer o controle de acesso.
