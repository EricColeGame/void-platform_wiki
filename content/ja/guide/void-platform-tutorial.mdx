## 共有デプロイ先がチームのワークフローを変える理由

チーム向けの共有デプロイ先を立ち上げるのは、最初の開発者が「ロールバック履歴はどこへ行った？」と尋ねてくるまでは簡単に見えます。Void Platform のチュートリアルはそのギャップを埋めます。共有 Cloudflare アカウント上にセルフホスト型プラットフォームをインストールし、すべての開発者が同じ管理された環境へデプロイできるように導きます。この Void Platform チュートリアルでは、前提条件、認証情報、コアのインストール、そしてほとんどのチームが最終的に必要とするオプションサービスを扱います。

まずひとつ明確にしておきます。自分のアプリをリリースするのにプラットフォームは必要ありません。自分自身のためにデプロイするなら、ツールを直接 Cloudflare に向ければ済みます。プラットフォームが価値を発揮するのは、複数の人が共有アクセス、保持されるデプロイ履歴、そして何かが壊れたときに確認できる一貫した場所を必要とする場合だけです。

この区別が重要なのは、それが以降のあらゆる判断を形作るからです。どれだけインフラを用意するかから、オプションサービスを有効にするかどうかまで。

## Void Platform が実際に何をするのか

Void プラットフォームはインストールするものであり、SaaS のサインアップではありません。管理者として、チームで共有する Cloudflare アカウントにそれをインストールし、その後継続的に維持します。開発者は Void CLI をプラットフォームの URL に接続し、有効化したログイン方法のいずれかでサインインし、デプロイします。開発者側で Cloudflare アカウントをやりくりする必要はありません。

プラットフォームレイヤーは、直接デプロイにはない2つのものを追加します。チーム全体の共有アクセスと、ライブログのテールを超えて保持されるデプロイ履歴です。それ以外はすべて設定です。

| 状況 | 推奨されるターゲット | 理由 |
|---|---|---|
| 個人のサイドプロジェクトをリリースする | Cloudflare へ直接 | 管理者のオーバーヘッドなし、維持すべき共有物もなし |
| 2人以上の開発者が定期的にデプロイする | コアのセルフホスト型プラットフォーム | 共有アクセスと保持されるデプロイ記録 |
| 後からログが必要になる | コアのセルフホスト型プラットフォーム | ライブテールだけでなく実行時ログを保持する |
| 正常動作が確認されたビルドへロールバックしたい | コアのセルフホスト型プラットフォーム | 戻ることのできるデプロイを保持する |
| GitHub 駆動のビルドが必要 | Cloudflare へ直接、またはオプションサービス付きのソースビルド型プラットフォーム | マネージド GitHub ビルドは標準インストールには含まれない |

## 前提条件と認証情報：まずこれらを揃える

公式のインストールガイドが前提条件と認証情報を分けているのには理由があります。失敗するインストールのほとんどは、そのどちらかが欠けているのです。何かに触れる前にこのチェックリストを済ませておけば、この Void Platform チュートリアルの残りはずっと速く進みます。

| 要件 | 重要な理由 | 適用対象 |
|---|---|---|
| チームで共有する Cloudflare アカウント | プラットフォームはそこへアプリをデプロイする | プラットフォーム |
| プラットフォームアカウントでの Workers Paid | マネージド Sandboxes に必要 | プラットフォーム |
| Workers for Platforms と文書化されたインフラ | 完全なチームプラットフォームの運用に必要 | チームプラットフォーム |
| インストーラー用の API 認証情報 | インストールがあなたのアカウント上で動作するために必要 | プラットフォーム |
| 共有メールドメインとゾーン | メールゲートウェイを有効化する | オプションだが一般的 |
| 各開発者マシン上の Void CLI | 開発者が接続しデプロイする方法 | 開発者 |

このうち2行は過小評価されがちです。第一に、Workers Paid は Sandboxes の必須要件です。開発者の個人アカウントではなく、プラットフォームアカウントで具体的に計画してください。第二に、メールドメインとゾーンこそが実際にメールゲートウェイをオンにするものです。それがなければ、ゲートウェイは機能しないままです。

組織が API の前に Cloudflare Access を置いている場合、オプションの GitHub サービスを追加するソースビルド型プラットフォームには分離された Webhook イングレス設定が必要であることに注意してください。Webhook と対話型ログインは同じ保護されたパス上ではうまく共存できません。

## ステップバイステップ Void Platform チュートリアル：コアのインストール

インストール自体は単一のコマンドではなく、一連の手順です。正確なコマンドと認証情報の形式については[公式 Void セルフホスト型プラットフォームインストールガイド](https://void.cloud/guide/self-hosted-platform)に従い、以下の表をチェックリストとして使って何も飛ばさないようにしてください。

| ステップ | アクション | 得られる結果 |
|---|---|---|
| 1 | 共有 Cloudflare アカウントと Workers Paid の状態を確認する | 有効なプラットフォームアカウント |
| 2 | インストーラー用の認証情報を集める | インストールが認証に必要とするすべてのもの |
| 3 | そのアカウントへコアインストールを実行する | チームがアクセスできるプラットフォーム URL |
| 4 | 共有メールドメインとゾーンを設定する | 有効なメールゲートウェイ |
| 5 | マネージド Sandboxes が起動することを確認する | アプリのための動作する分離実行環境 |
| 6 | 開発者に使ってほしいログイン方法を有効化する | チームのためのサインイン経路 |
| 7 | プラットフォーム URL を開発者と共有する | 誰もがアクセスできるデプロイ先 |

### インストール後の開発者オンボーディング

あなたの仕事は「インストール済み」で終わりではありません。各開発者にはローカルにインストールされた Void CLI、プラットフォーム URL、そして動作するログイン方法が必要です。サポート連絡の90パーセントを防ぐ3行の引き継ぎ：

- **URL** — CLI が向くべき場所。
- **ログイン方法** — どの ID プロバイダーまたは認証情報を使うべきか。
- **期待値** — アプリは共有アカウントへデプロイされるため、リソース使用量は全員に見える。

これを DM ではなくピン留めメッセージとして送ってください。新入社員は後で感謝してくれますし、あなたは四半期ごとに同じ質問に答える必要がなくなります。

## コアインストールとオプションサービス

初日からダッシュボードと GitHub ビルドを約束する Void Platform チュートリアルは、標準インストールを誇張しています。コアは意図的にスリムです。実際に含まれるものはこちらです。

| コンポーネント | コアインストールに含まれる？ | 備考 |
|---|---|---|
| マネージド Sandboxes | はい | プラットフォームアカウントでの Workers Paid が必要 |
| メールゲートウェイ | はい、設定後 | 有効化には共有メールドメインとゾーンが必要 |
| ユーザーダッシュボード | いいえ | UI が必要なら別途追加 |
| GitHub ビルドと Webhook | いいえ | オプションサービス、通常はソースビルド型プラットフォーム上 |
| Build Containers | いいえ | デフォルトでは含まれない |
| カスタムプロジェクトドメイン | いいえ | コアの一部ではない |

これを事前に知っておけば、つらい会話を避けられます。洗練された管理 UI をすぐに使えると期待するチームは、インストールが「失敗した」と結論づけがちですが、実際にはコアインストールが提供するもの、つまり共有アクセスと保持された履歴を備えたデプロイ先、それ以上でも以下でもないものを得ているだけなのです。

## 直接 Cloudflare とセルフホスト型 Void Platform の比較

どちらのターゲットも同じアプリケーション API を使うため、両者の間を移動することは書き直しではありません。違いは運用面に現れます。以下の比較は、2つのターゲットが実際にどう振る舞うかを反映しています。

| 機能 | Cloudflare へ直接 | コアのセルフホスト型プラットフォーム |
|---|---|---|
| Workers AI とプロバイダーリクエスト | あなたのアカウントとゲートウェイ | インストールのゲートウェイとプロキシ |
| 実行時ログ | Cloudflare のライブテール | 保持されるプラットフォームログ |
| アプリケーションのロールバック | Worker バージョン | 保持されるプラットフォームデプロイ |
| Sandboxes | Workers Paid と Docker | プラットフォームアカウントでの Workers Paid |
| ユーザーダッシュボードとマネージド GitHub ビルド | 不要 | 標準インストールには含まれない |

実用的な結論：管理する範囲をゼロにしたいなら直接デプロイを選び、シンプルさよりも保持と共有アクセスを重視するならプラットフォームを選んでください。間違った答えはありません。あるのはミスマッチだけです。

## 注意すべき落とし穴

Void Platform チュートリアル中に人が遭遇する問題のほとんどは、インストール自体ではなく設定に起因します。コミュニティの報告と管理者の経験は、同じいくつかの症状に集中する傾向があります。

| 症状 | 考えられる原因 | 対処法 |
|---|---|---|
| メールがまったく届かない | 共有メールドメインとゾーンが未設定 | 両方を設定してゲートウェイを有効化する |
| Access 背後で GitHub Webhook が失敗する | 保護された API パスが Webhook 呼び出しを飲み込んでいる | 分離された Webhook イングレス設定を使う |
| Sandboxes が起動しない | プラットフォームアカウントに Workers Paid がない | プラットフォームが動作するアカウントをアップグレードする |
| 開発者がサインインできない | ログイン方法が有効化されていない、または URL が間違っている | 方法を有効化し、プラットフォーム URL を再共有する |
| 「ダッシュボードはどこ？」 | 期待値のミスマッチ | コアインストールの範囲を説明する、またはオプションサービスを追加する |
| ロールバック履歴が空に見える | プラットフォーム経由ではなく直接デプロイしている | CLI をプラットフォーム URL に向ける |

もうひとつのヒント：認証情報は耐久性がありアクセス制御された場所に文書化しておいてください。インストールは繰り返せますが、6か月後にどの認証情報がどの環境のものかを覚えていることは、繰り返せない部分です。

## よくある質問

**自分のアプリだけをデプロイする場合、Void Platform チュートリアルは必要ですか？**

いいえ。Cloudflare へ直接デプロイすることがソロ作業には正しい選択です。インストール、管理者の仕事、共有アカウントのオーバーヘッドを完全に省けます。プラットフォームはチームのツールであり、前提条件ではありません。

**コアインストールには実際何が含まれますか？**

マネージド Sandboxes とメールゲートウェイで、メールは共有メールドメインとゾーンを設定すると有効になります。ユーザーダッシュボード、GitHub ビルドと Webhook、Build Containers、カスタムプロジェクトドメインはすべてコアの外です。

**プラットフォームが稼働したら、開発者はどう接続しますか？**

Void CLI をインストールし、プラットフォーム URL に向け、有効化されたログイン方法でサインインし、デプロイします。開発者側で個別の Cloudflare アカウント設定は不要です。

**この Void Platform チュートリアルはチーム規模のプラットフォームを扱っていますか？**

コアインストールを扱っており、それが基盤です。完全なチームプラットフォームの運用にはさらに Workers for Platforms と文書化されたインフラが必要です。スケールアップする前に [Workers for Platforms ドキュメント](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/)を確認してください。

**管理者が犯す最大の間違いは何ですか？**

コアインストールに UI とマネージドビルドが含まれていると思い込むことです。チームと早い段階で期待値をすり合わせ、必要なオプションサービスを意図的に決めれば、プラットフォームは設計どおりに動作します。つまり、全員にデプロイのためのひとつの場所を提供し、実際にロールバックできる履歴を備えるということです。
