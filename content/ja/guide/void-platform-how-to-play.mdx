## Void Platformとは実際何なのか

「Void Platform how to play」で検索したなら、おそらくゲームを期待したはずです。そしてある意味では、その通りです。Void Platformはオープンソースのランタイムで、すべてのAIエージェント実行を専用の使い捨てmicroVMの中に置き、最初の一手の前にルールを宣言します。共有カーネルもなく、あなたのマシンへの暗黙のアクセスもなく、ラウンドが終わった後にエージェントが何に触れたかを推測する必要もありません。

このVoid Platform how to playガイドでは、インストールから最初の封じ込められた実行までを案内し、その後、物事がクリーンに進んだかどうかを教えてくれるテレメトリの読み方を示します。核心となる考え方は、生成が難しい部分ではなかったということです。難しいのは制御です。エージェントがシェルを開き、ファイルを編集し、APIを呼び出せるようになると、有用な問いは「役に立ったか？」ではなく「間違ったとき、何がそれを封じ込めているのか？」になります。

このフレーミングの転換こそが、このプラットフォームをツールというより、固定されたルールを持つゲームのように感じさせる理由です。

| 構成要素 | 内容 | 重要な理由 |
| --- | --- | --- |
| Void-Box | 使い捨てのmicroVMランタイム | 1回の実行に専用の境界が1つ与えられる |
| ゲストカーネル | VM内の分離されたカーネル | ホストとカーネルを共有しない |
| ケイパビリティゲート | コマンド、ファイル、ネットワーク、制限の明示的な宣言 | 暗黙的・暗示的なものは一切ない |
| OCI rootfs | イメージにオーバーレイとスナップショット/リストアを加えたもの | 毎回再現可能なゲスト |
| OTLPテレメトリ | トレース、メトリクス、構造化イベント | 実行後も検査可能なまま |
| Void-Control | 多数の実行を扱うオペレーター層 | パイプラインの調整とステージの検査 |

メンタルモデルは驚くほどシンプルです。エージェントが何をするかを決め、ランタイムが何に触れられるか、どこで動くか、後で何を検査できるかを決めます。ケイパビリティは実行前に宣言され、各実行は独自の境界に入り、ログ、トレース、出力はその間ずっと観測可能なままです。

## 最初の実行の前に：必要なもの

セットアップは意図的に小さくまとまっています。立ち上げるコントロールプレーンも、作るベンダーアカウントもありません。プロジェクトはApache 2.0ライセンスで、ベンダーニュートラルになるよう設計されているため、同じランタイムがローカルでもリモートハードウェアでも動作します。

| 要件 | 詳細 |
| --- | --- |
| ホストオペレーティングシステム | KVM対応Linux、またはApple Silicon上のmacOS |
| 現在のリリース | v0.2.0（執筆時点の最新） |
| インストール | 公式サイトで公開されているワンラインインストールスクリプト |
| ライセンス | Apache 2.0、オープンソース |
| エージェント互換性 | 既存のCLIエージェント、または同じランタイム上のリモートエージェント |
| 実行場所 | ローカルまたはリモート、選択可能 |

始める前に実用的な注意点が2つあります。第一に、インストーラーは[Void Platform公式サイト](https://voidplatform.ai/)からのみダウンロードし、シェルにパイプする前にスクリプトを読んでください。これは不信ではなく、基本的な衛生習慣です。第二に、ハードウェアを確認してください。プラットフォームが挙げているのはLinux KVMとApple Silicon macOSなので、古いIntel Macはサポート対象のホストではありません。ノートPCがIntelベースなら、代わりにLinuxマシンでランタイムを動かしてください。

## Void Platform how to play：最初の分離実行

Void Platform how to playを学ぶ最速の方法は、一度の作業で終わるくらい小さなタスクを選ぶことです。単一の調査質問、小さなリファクタリング、スクリプトによるファイル整理のいずれも適しています。最も複雑なパイプラインから始めたい衝動は抑えてください。

| ステップ | アクション | 良い結果とは |
| --- | --- | --- |
| 1 | ランタイムをインストールする | インストーラーが完了し、ランタイムが応答する |
| 2 | CLIエージェントを1つ選ぶ | そのエージェントの挙動をすでに把握している |
| 3 | 短いケイパビリティリストを書く | すべての項目に、声に出して説明できる理由がある |
| 4 | 実行を起動する | 新しいmicroVMが起動し、インタラクティブなPTYシェルが現れる |
| 5 | シェル内で作業する | エージェントは宣言されたスコープ内にとどまる |
| 6 | 出力を検査する | トレース、ログ、アーティファクトが保存される |
| 7 | VMを終了させる | 境界が閉じ、何も残らない |

### 1つのボックスに収まるタスクを選ぶ

良い最初の実行は、結果を目視で確認できるほど狭いものです。たとえば、コーディングエージェントをラップしてリポジトリを要約させるのは、よく境界づけられたタスクです。1つのディレクトリへの読み取りアクセスが必要で、外向きネットワークは不要、CPU上限も控えめで済みます。エージェントがそれ以上を求めてきたら、ツールではなくタスクについて有用なことを学んだということです。

ここでスナップショットとリストアが重要になります。ランタイムは毎回フルVMを起動するのではなくスナップショットから復元するため、反復が十分速く、実験が面倒に感じられません。

## ゲームのルール：ケイパビリティの宣言

プロンプトの規律は分離ではありません。指示はエージェントが取り込むあらゆるものによって誘導されうるため、誠実なVoid Platform how to playのチュートリアルはプロンプトではなく権限から始まります。権限は善意から推測されるのではなく、ランタイムによって強制されなければなりません。

| ケイパビリティ | 与えるもの | 妥当な出発点 |
| --- | --- | --- |
| ファイルシステムマウント | 特定パスへの読み書き | 作業ディレクトリを1つ、可能なら読み取り専用 |
| ネットワークエグレス | 外向き接続 | デフォルトで拒否し、その後特定ホストを許可リストに追加 |
| ツールとスキルのマウント | エージェントに見えるCLIとスキル | タスクが本当に必要とするものだけ |
| リソース制限 | CPUとメモリの上限 | 使い捨ての実験でも上限を設定する |
| シークレット | ゲスト内の認証情報 | デフォルトはなし、避けられない場合は短命トークン |

ケイパビリティを承認する前に、3つの質問をしてください。このタスクはそれがなければ失敗するか？ 注入された指示がそれを使って最悪何をしうるか？ そしてそれが起きたら自分は気づけるか？ 3つ目の答えが「いいえ」なら、あなたに足りないのは権限ではなく可観測性です。

## コンテナでは守れない境界が守れる理由

コンテナは既知の攻撃のほとんどに対して堅牢化でき、多くのチームがまさにそうしています。違いはデフォルトにあります。コンテナベースのエージェントはホストカーネルを共有するため、1つの設定ミスが広い爆発半径を持ちます。Void Platform how to playのウォークスルーが分離の話に何度も戻ってくるのは、封じ込めが適切な設定だけでなく、失敗に耐えなければならないからです。

| 攻撃 | コンテナベースのエージェント | Void-Box実行 |
| --- | --- | --- |
| プロンプトインジェクション | 環境内の暗黙のシークレットが漏洩しうる | ホストの暗黙のシークレットは存在しない |
| Dockerソケットエスケープ | マウントされたソケットがホストの完全な制御を与える | ソケットが存在しない |
| 特権コンテナ | ホストのディスクとデバイスに到達可能 | デフォルトでホストデバイスなし |
| cgroupエスケープ | ホスト上のバイナリを実行できる | ゲストカーネルのみ |
| メタデータSSRF | クラウドメタデータサービスが認証情報を渡す可能性がある | メタデータに到達不能 |

この表はスコアボードではなく設計声明として読んでください。要点は、実行がコースを外れたとき、結果は目に見える証拠を伴う封じ込められたインシデントであるべきで、あなたのノートPCへの暗黙のアクセスであってはならないということです。

## スコアボードを読む：トレース、メトリクス、ログ

可観測性は、初心者が飛ばし、熟練のオペレーターが決して飛ばさないVoid Platform how to playの部分です。実行はエージェントがタイピングをやめたときに終わるのではなく、何が起きたかを説明できるときに終わります。

| シグナル | 得られるもの | 答える質問 |
| --- | --- | --- |
| OTLPトレース | 実行とステージに相関したステージごとのスパン | 時間は実際どこに消えたか？ |
| OTLPメトリクス | ステージごとのトークン、コスト、所要時間 | この実行にいくらかかったか？ |
| 構造化イベント | box.started、box.completed、stage.error | 何が、どの順序で起きたか？ |
| vsock経由のprocfsテレメトリ | ゲスト内部からのCPUとメモリ | 実行は上限に達したか？ |
| アーティファクト | 出力、ログ、構造化イベント | 何を生成したか？ |

- **トレースは実行に属する**のであり、共有サンドボックスに属するのではないため、相関は曖昧になりません。
- **アーティファクトはVMを越えて残る**ため、ゲストが消えたずっと後でも実行を監査できます。
- **境界イベントはホストとゲストの活動から生まれる**ため、あなたは物語を再構成するのではなく証拠を読んでいます。

## レベルアップ：Void-Controlで多数の実行を調整する

封じ込めは実行単位ですが、実際の仕事は多数の実行です。Void-Controlは、Void-Box実行を生成し、ステージをまたいで調整し、それぞれが何に触れたかを示すオペレーター層です。ターミナルファーストで、コマンドラインから実行を操作し、コンテキストを失わずに任意のステージへ掘り下げられます。実行グラフの可視性により、ステージの関係とパスが一目で読めるようになります。これが、パイプラインをデバッグすることと推測することの違いです。

より長いものを作る前に、まず2ステージのパイプライン（たとえば調査、次にドラフト）から始めてください。各ステージが独自の境界を持つため、失敗がローカルにとどまり、グラフを推論しやすくなります。

## クリーンな実行と乱雑な実行を分ける習慣

| 間違い | 症状 | 修正 |
| --- | --- | --- |
| 1つの長寿命ボックスを使い回す | タスク間で権限がじわじわ拡大する | 常に1タスク1実行 |
| ネットワークエグレスを与えすぎる | エージェントが不要なものに到達する | デフォルトで拒否し、ホストを許可リスト化 |
| リソース制限を省略する | ゲスト内の挙動が乱れる | CPUとメモリの上限を早めに設定する |
| トレースを決して読まない | 「たぶん動いた」 | スケールアップ前にスパンを読む |
| 非対応ハードウェアでテストする | 起動失敗が混乱を招く | Linux KVMまたはApple Silicon macOSを使う |

Void Platform how to playの旅の早い段階で身につける価値のあるもう1つの習慣は、各エージェントが何に触れることを許されたかの短い記録を書いておくことです。実行が誤動作したとき、そのメモとトレースがあれば、謎は5分の確認作業に変わります。

## FAQ

**Void Platform how to playを学ぶにはLinuxが必要ですか？**
いいえ。ランタイムはKVM対応LinuxとApple Silicon上のmacOSをサポートしています。Intel Macを使っている場合は、その組み合わせは対応プラットフォームに含まれていないため、代わりにLinuxマシンを使用してください。

**エージェントワークロードにおいて、microVMはコンテナとどう違うのですか？**
コンテナはホストカーネルを共有するため、設定ミスがホストを露出させる可能性があります。各Void-Box実行は独自のゲストカーネルを取得し、共有境界もホストのシークレットやデバイスへの暗黙のアクセスもありません。

**最初のケイパビリティリストには何を含めるべきですか？**
ファイルシステムマウントを1つ、ネットワークはデフォルトで拒否、そしてリソース上限から始めてください。ツールはタスクがそれなしで失敗するときにだけ追加し、後から検出できないアクセスは決して許可しないでください。

**Void Platform how to playの学習曲線はどこで急になりますか？**
ほぼ常にマルチステージパイプラインです。単一の実行は straightforward ですが、複数を調整する段階で、実行グラフの可視性と一貫したケイパビリティ宣言が効き始めます。
