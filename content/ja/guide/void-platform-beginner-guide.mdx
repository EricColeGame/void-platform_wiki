## Void Platform とは実際何なのか

チーム向けの共有デプロイ基盤を立ち上げるのは、通常なら一週間の配管作業のように聞こえますが、Void Platform はそれをガイド付きインストールに圧縮します。各開発者が自分の Cloudflare アカウントを接続する代わりに、一度インストールするだけで、チーム全体にアプリを出荷する単一の場所を提供でき、ログとロールバック履歴も保持されます。この Void Platform 初心者ガイドでは、プラットフォームとは何か、始める前に必要なもの、そして最初の開発者が迷わずデプロイできるようにする方法を説明します。

核となる考え方はシンプルです。Void プラットフォームは、1 つの Cloudflare アカウント内に存在する共有デプロイ先です。管理者がインストールして保守します。開発者は Void CLI をプラットフォームの URL に接続し、有効になっている任意のログイン方法でサインインして、アプリをデプロイします。プラットフォームが共有の配管を処理するため、誰もプロジェクトごとに認証、ルーティング、リリース履歴を再解決する必要はありません。

初心者の時間を大幅に節約する重要な注意点が 1 つあります。自分だけでアプリをデプロイするなら、プラットフォームはまったく必要ありません。Cloudflare に直接デプロイしてください。Void Platform は、複数の人がインフラを共有し、一貫したアクセスと何が出荷されたかの記録を必要とするときに真価を発揮します。

### 共有プラットフォームが価値を持つのはどんなときか

- 2 人以上の開発者が同じ Cloudflare アカウントにデプロイしている
- ライブのみのログではなく、保持されたデプロイ履歴が必要
- ロールバックが手動の Worker バージョン探しではなく、プラットフォームの操作であるべき
- 許可するログイン方法を一元管理したい

## Cloudflare への直接デプロイとコアのセルフホスト Void Platform の比較

どちらのターゲットも同じアプリケーション API を使用するため、一方で動作するアプリは通常もう一方でも動作します。違いはアプリを囲むものです。共有アクセス、保持された履歴、プロバイダーリクエストをプロキシするゲートウェイです。以下の表は公式の比較を言い換えたものです。

| 機能 | Cloudflare へ直接 | コアのセルフホスト Void Platform |
| --- | --- | --- |
| Workers AI とプロバイダーリクエスト | 自分のアカウントとゲートウェイ | インストールのゲートウェイとプロキシ |
| ランタイムログ | Cloudflare のライブテール | 保持されたプラットフォームログ |
| アプリケーションのロールバック | Worker バージョン | 保持されたプラットフォームデプロイ |
| Sandboxes | Workers Paid と Docker が必要 | プラットフォームアカウントで Workers Paid が必要 |
| ユーザーダッシュボードとマネージド GitHub ビルド | 不要 | 標準インストールには含まれない |

Void Platform 初心者ガイドを初めて読む人への実用的な要点は、ソロなら直接デプロイから始め、コーディネーションがボトルネックになった時点でプラットフォームに移行することです。後から移行するほうが、まだ必要のないインフラを維持するよりはるかに楽です。

## 前提条件：インストール前に揃えておくもの

最初のインストールの失敗のほとんどは技術的な失敗ではなく、前提条件の欠落です。公式のインストールドキュメントはこれを前提条件と認証情報に分けています。どちらも流し読みではなくチェックリストとして扱う価値があります。

| 要件 | 重要な理由 | 初心者向けメモ |
| --- | --- | --- |
| プラットフォーム専用の Cloudflare アカウント | すべての共有デプロイがここに配置される | 個人プロジェクトを混ぜない |
| プラットフォームアカウントの Workers Paid | これがないと Sandboxes が実行されない | インストール前にプランを確認 |
| Workers for Platforms | 真のチームプラットフォームに必要 | マルチテナント構成でのみ必要 |
| メール用のドメインとゾーン | 設定した場合にのみメールゲートウェイが有効になる | 省略するとメールはオフのまま |
| 開発者マシン上の Void CLI | 開発者がデプロイする主な方法 | オンボーディングの日に備えてインストール |
| インストール用の管理者認証情報 | プラットフォームのブートストラップと保守に必要 | 共有かつ監査可能な場所に保存 |

### 多くの人が見落とす前提条件

メールは典型的な落とし穴です。コアインストールにはメールゲートウェイが含まれていますが、共有メールドメインとゾーンを設定して初めて有効になります。チームはインストールしてテストし、なぜメールが届かないのかと不思議に思います。メールが必要かどうかを事前に決め、必要なら初日からドメインを用意しておきましょう。

## Void Platform を正しい順序でインストールする

順序は速度より重要です。以下の手順は公式ガイドの構成に従っており、まだ構築していないものに依存する機能を設定してしまうのを防ぎます。

| ステップ | 行うこと | この順序である理由 |
| --- | --- | --- |
| 1 | 前提条件ページを最後まで読む | インストール中の予期せぬ事態を防ぐ |
| 2 | 認証情報を集めて保存する | インストールですぐに必要になる |
| 3 | コアのみか拡張スコープかを決める | 後で設定する内容が変わる |
| 4 | コアインストールを実行する | Sandboxes とメールゲートウェイを提供する |
| 5 | 共有メールドメインとゾーンを設定する | メールゲートウェイを有効にする |
| 6 | プラットフォームへの管理者アクセスを確認する | 保守できることを確認する |
| 7 | Void CLI をプラットフォーム URL に接続する | 開発者の入口 |
| 8 | 有効なログイン方法でサインインする | 認証がエンドツーエンドで機能することを確認する |
| 9 | 使い捨てのテストアプリをデプロイする | オンボーディング前に全経路を検証する |

ステップ 7 から 9 は、初心者が急いでしまう部分です。小さなアプリを 1 つデプロイしてからロールバックする 5 分間のスモークテストで、記憶が新しいうちに設定上の問題を捕まえられます。公式の [Void セルフホストプラットフォームインストールガイド](https://void.cloud/guide/self-hosted-platform) に従う場合は、この Void Platform 初心者ガイドの横に開いて上から順に進めてください。

## コアインストールに含まれるもの — 含まれないもの

標準インストールは意図的に最小限です。境界を知っておけば、そもそも作られていないメニューを探し回らずに済みます。

| コアインストールに含まれる | 標準インストールには含まれない |
| --- | --- |
| マネージド Sandboxes | ユーザーダッシュボード |
| メールゲートウェイ（メールドメインとゾーンを設定した後） | マネージド GitHub ビルドと Webhook |
| チームの共有アクセス | Build Containers |
| 保持されたデプロイ履歴とログ | カスタムプロジェクトドメイン |

不足している機能が必要な場合は、オプションサービスを通じて追加します。これは最も一般的にはソースビルドのプラットフォームで行われます。ドキュメントからの注意点が 1 つあります。ソースビルドのプラットフォームにオプションの GitHub サービスを追加し、Cloudflare Access が API を保護している場合は、分離された Webhook イングレス構成を使用してください。そうしないと Webhook トラフィックと Access ポリシーが衝突し、ビルドが不可解な形で失敗します。

共有プラットフォームを運用しているチームからのコミュニティ報告は、1 つの点で一致する傾向があります。オプションサービスは一度に 1 つずつ追加し、追加するたびにテストアプリをデプロイするということです。テスト前に 3 つの新しいサービスを積み重ねると、単純な設定ミスが長いデバッグ作業になってしまいます。

## よくある摩擦なしで開発者をオンボーディングする

管理者の仕事はインストールで終わりません。開発者には 3 つが必要です。プラットフォーム URL、有効なログイン方法、動作する CLI です。

- **プラットフォーム URL を明示的に共有する。** ブックマークでも、3 か月前の Slack メッセージでもなく、チームのドキュメントに記載してください。
- **有効なログイン方法を確認してから** サインインするよう伝えましょう。有効にしていない方法で誰かが足止めされるのを防げます。
- **CLI のセットアップを標準化する。** インストール、接続、サインインをカバーする 1 ページの社内メモがあれば、同じ質問に 5 回答えるより効率的です。
- **デプロイの慣習を決める。** 命名やロールバックの期待値に関する軽量なルールでも、履歴が蓄積されるほど効果を発揮します。

120 語未満の段落 — 問題ありません。また、チームプラットフォームは Workers for Platforms とドキュメント化されたインフラに依存するため、機能は構成によって異なることも覚えておく価値があります。自分のプラットフォームがチュートリアルと同じように動作すると決めつけず、自分のインストールで実際に何が有効になっているかを確認してください。

## 最も時間を無駄にする初心者のミス

| ミス | どのように見えるか | 修正方法 |
| --- | --- | --- |
| ソロプロジェクト用にプラットフォームをインストールする | メリットのない余分なインフラ | 代わりに Cloudflare へ直接デプロイする |
| ダッシュボードを期待する | インストールされていない UI を探す | オプションサービスを計画するか、CLI ファーストで進める |
| プラットフォームアカウントの Workers Paid を忘れる | Sandboxes が実行を拒否する | 正しいアカウントでプランを確認する |
| ドメインとゾーンなしでメールを有効にする | メールが黙って送信されない | 先に共有メールドメインを設定する |
| テストデプロイを省略する | オンボーディング中に問題が表面化する | 使い捨てアプリを 1 つデプロイしてロールバックする |

5 つすべての背後にあるパターンは同じです。「インストール済み」とは何を意味するかについての思い込みです。Void Platform 初心者ガイドは、ここまでしか助けられません。残りは、一般的な説明を信じるのではなく、自分の特定の構成を確認することです。

## よくある質問

**アプリをデプロイするのに Void Platform は必要ですか？**
いいえ。自分用にデプロイする場合は、Cloudflare に直接デプロイし、プラットフォームは完全に省略してください。Void Platform は、共有アクセスと保持されたデプロイ履歴を求めるチーム向けです。

**最初のインストールにはどのくらいかかりますか？**
前提条件リストのうち、すでにどれだけ対応しているかによります。認証情報を集め、Cloudflare プランを事前に確認しているチームはコアインストールを素早く進められます。途中で不足要件に気づくチームは、しばしばやり直しになります。

**標準インストールから欠けているものは何ですか？**
ユーザーダッシュボード、マネージド GitHub ビルドと Webhook、Build Containers、カスタムプロジェクトドメインはすべてコアインストールの対象外です。Sandboxes とメールゲートウェイは含まれますが、メールは共有メールドメインとゾーンを設定して初めて有効になります。

**開発者は悪いデプロイをロールバックできますか？**
はい。コアのセルフホストプラットフォームでは、ロールバックは生の Worker バージョンではなく、保持されたプラットフォームデプロイを使用します。これはチームが場当たり的な直接デプロイではなく、Void Platform 初心者ガイドのアプローチを採用する主な理由の 1 つです。

**初心者はどこから始めるべきですか？**
前提条件と認証情報のページを読み、プランとアカウント設定を確認してから、コアをインストールし、小さなアプリ 1 つで検証してください。それ以外は後から積み重ねられます。
