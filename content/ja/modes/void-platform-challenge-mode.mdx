チームが単一アプリのデプロイを超えた瞬間、楽な道は消えます。Void Platformチャレンジモードとは、その一段難しい作業領域を指すための略称です。つまり、Workerを自分のCloudflareアカウントへ直接送り込むのではなく、他の開発者が依存する共有プラットフォームをインストールして維持するという作業です。これを正しく実現すれば、チーム全員が1つのURLを通じて接続し、承認された1つの方法でサインインし、保持されたデプロイ履歴に対してリリースできるようになります。だからこそVoid Platformチャレンジモードは、個人の習慣を信頼できる内部インフラへ変えることだと言えます。

## 実践における「Void Platformチャレンジモード」の意味

まず誤解を解いておきましょう。チャレンジモードというラベルが付いたダッシュボードのトグルやチェックボックスは存在しません。このフレーズは、高度な設定層を指す実用的なラベルです。つまり、単なるデプロイ担当者ではなく、管理者として作業する構成です。その層では、インストール、ログイン方法、メールドメイン、アップグレード経路、そして午前2時に何かが壊れたときのオンコール体制まで、すべてを自分たちで所有します。

この区別が重要なのは、どちらの経路も同じアプリケーションAPIを使うからです。開発者の日々のコマンドはほとんど変わりません。変わるのは、その周囲のすべてです。誰が認証情報を保持するのか、ログはどこに存在するのか、ロールバックはどう機能するのか、そしてどのオプションサービスがそもそも存在するのか、といった点です。

| 観点 | ソロ構成（Cloudflareへ直接） | Void Platformチャレンジモード（セルフホスト） |
| --- | --- | --- |
| インストールする人 | なし — デプロイするだけ | 管理者がプラットフォームをインストールして維持 |
| デプロイできる人 | 自分 | プラットフォームURLと有効なログイン方法を持つ任意の開発者 |
| AI／プロバイダーリクエストのルーティング先 | 自身のアカウントとゲートウェイ | インストール環境のゲートウェイとプロキシ |
| ログ | Cloudflareでのライブテール | 保持されたプラットフォームログ |
| ロールバック | Workerバージョン | 保持されたプラットフォームデプロイ |
| 障害の影響範囲 | 1つのアプリ | プラットフォーム上のすべてのアプリ |

最後の行が最重要ポイントです。ソロ構成では、ミスをしても影響するのは1回のデプロイだけです。Void Platformチャレンジモードでは、設定を誤ったイングレスや期限切れの認証情報が、チーム全体を止めてしまう可能性があります。

## コアプラットフォームとCloudflare直接利用：実際に変わること

標準インストールは意図的に最小限です。マネージドサンドボックスとメールゲートウェイが含まれますが、メールは共有メールドメインとそのゾーンを設定して初めて有効になります。標準搭載だと思われがちなもののうち、ユーザーダッシュボード、マネージドGitHubビルドとウェブフック、ビルドコンテナ、カスタムプロジェクトドメインは、コアインストールにはまったく含まれません。

ソースからビルドし、オプションのGitHubサービスを追加する場合は、イングレスに注意してください。Cloudflare AccessがAPIを保護している場合、それらのウェブフックエンドポイントは、保護されたメインルートに相乗りするのではなく、分離されたウェブフックイングレスのパターンが必要です。この手順を飛ばすと、APIは完璧に正常に見えるのにビルドが永遠にキューに溜まるという、典型的な症状が発生します。

| 機能 | Cloudflareへ直接 | コアのセルフホストプラットフォーム |
| --- | --- | --- |
| Workers AIとプロバイダーリクエスト | 自身のアカウントとゲートウェイ | インストール環境のゲートウェイとプロキシ |
| ランタイムログ | Cloudflareのライブテール | 保持されたプラットフォームログ |
| アプリケーションのロールバック | Workerバージョン | 保持されたプラットフォームデプロイ |
| サンドボックス | Workers PaidとDockerが必要 | プラットフォームアカウントでWorkers Paidが必要 |
| ユーザーダッシュボードとマネージドGitHubビルド | 必須ではない | 標準インストールには含まれない |

計画上の注意をもう1点。本物のチームプラットフォームには、Workers for Platformsと、その周辺の文書化されたインフラが必要です。そのうえで機能の可用性は、インストールの構成方法に完全に依存します。したがって、開発者にURLを渡す前に、選択内容を書き留めておいてください。

## Void Platformチャレンジモード環境のセットアップ

ロールアウトは、自由に並列化できるチェックリストではなく、順序として扱ってください。各ステップが次のステップを解き放ち、先へ飛ばすことがほとんどの苦痛の原因になります。

| 手順 | アクション | この順序になる理由 |
| --- | --- | --- |
| 1 | プラットフォームアカウントのWorkers Paidを含む前提条件を確認する | これがないとサンドボックスは実行できない |
| 2 | プラットフォームとそれを支えるサービスの認証情報を準備する | 後続のすべてがこれらに対して認証を行う |
| 3 | コアプラットフォームをインストールし、応答することを確認する | 開発者が使用するベースURLを確立する |
| 4 | 共有メールドメインとゾーンを設定する | メールゲートウェイを未稼働状態から有効にする |
| 5 | 有効にするログイン方法を決める | 1つでも利用可能になるまで開発者は接続できない |
| 6 | Void CLIをプラットフォームURLに接続してサインインする | 完全な経路をエンドツーエンドで証明する |
| 7 | オプションサービス（GitHubビルド、ウェブフック、コンテナ）を個別に追加する | コアと追加機能を独立してデバッグできるようにする |

ここでは2つの習慣が報われます。第一に、URLを告知する前に自分でCLI接続をテストすることです。5分の確認で、混乱したメッセージが十数件も減ります。第二に、有効にしたオプションサービスとそのイングレスの場所を文書化することです。半年後には、ウェブフックルートが分離されていたかどうかなど、誰も覚えていないからです。

また、はっきり言っておくべき正当な「やらないこと」もあります。純粋に自分のためだけにアプリをデプロイするなら、プラットフォームは完全に飛ばしてCloudflareへ直接デプロイしてください。不要な共有インフラを立ち上げることは、Void Platformチャレンジモードで最もよくある自滅的な難しさです。

## Void Platformチャレンジモードのよくあるシナリオと修正

この層での失敗のほとんどは、バグではなく設定の不一致です。以下の表は、症状を考えられる原因に対応付けています。

| 症状 | 考えられる原因 | 修正 |
| --- | --- | --- |
| 開発者がサインインできない | ログイン方法が有効になっていない、またはCLIが誤ったURLを指している | ログイン方法を有効にし、プラットフォームURLを再確認する |
| メールが送信されない | 共有メールドメインまたはゾーンが設定されていない | ゲートウェイのドメインとゾーンの設定を完了する |
| サンドボックスが起動しない | プラットフォームアカウントにWorkers Paidがない、または必要な場所にDockerがない | プラットフォームアカウントのプラン状態を確認する |
| ビルドが無期限にキューに溜まる | Accessの背後でウェブフックに到達できない | GitHubサービスを分離されたウェブフックイングレスに移動する |
| カスタムドメインが何も返さない | カスタムプロジェクトドメインはコアインストールに含まれない | その機能を意図的に追加するか、デフォルトルートを使用する |
| 「ダッシュボードはどこ？」 | 標準インストールには含まれない | コアの前提ではなくアドオンとして計画する |

セルフホスト型デプロイプラットフォームを運用するチームからのコミュニティ報告も同じテーマを裏付けています。問題はプラットフォーム自体であることはほとんどなく、プラットフォームとIDまたはイングレス層の境界にインシデントが集中します。監視の注意をそれに応じて配分してください。

## Void Platformチャレンジモードでの運用：ログ、ロールバック、可観測性

プラットフォームが稼働したら、仕事はインストールから運用へ移ります。保持されたプラットフォームログは最大の利点です。ターミナルを閉じると消えるライブテールを追いかける代わりに、後からクエリできる履歴が得られます。ロールバックも同じです。保持されたプラットフォームデプロイを使えば、Workerバージョンを手作業で再構築することなく、以前のリリースへ戻れます。

| 運用タスク | ソロ構成 | Void Platformチャレンジモード |
| --- | --- | --- |
| リグレッションのデバッグ | ライブテールに接続する | 保持されたプラットフォームログを検索する |
| ロールバック | Workerバージョンを選択する | 保持されたデプロイを昇格する |
| 開発者のオンボーディング | アカウントアクセスを共有する | URLと有効なログイン方法を共有する |
| 何がリリースされたかの監査 | 手動で再構築する | デプロイ履歴を読む |

### 短い運用チェックリスト

- プラットフォームの認証情報はローテーションし、チャットスレッドや共有ドキュメントの外で保管する。
- ID変更後も、依存しているログイン方法が引き続き機能することを確認する。
- 共有ドメインまたはゾーンを編集した後は、メールゲートウェイを再テストする。
- オプションサービスは独自のイングレスに置き、ウェブフックの障害がコアのデプロイに影響しないようにする。
- アップグレード後は公式の[Voidプラットフォームインストールガイド](https://void.cloud/guide/self-hosted-platform)を再読する — 設定の詳細は進化する。
- チームプラットフォームを運用する場合は、Workers for Platformsのドキュメントを自チームのランブックと組み合わせる。

もう1つアドバイスです。必要になる前にロールバックを練習してください。Void Platformチャレンジモードでは、10分の復旧と2時間のインシデントの差は、通常、どの保持デプロイを昇格すべきかを誰かがすでに知っているかどうかにかかっています。

## よくある質問

### Void Platformチャレンジモードは公式機能ですか？

いいえ。これはセルフホスト型Void Platformの、管理者が所有する高度な構成層を指す実用的なラベルです。機能自体は実在します — 保持ログ、保持デプロイ、マネージドサンドボックス、ゲートウェイ、メールゲートウェイ — ただし「チャレンジモード」という名前は、より難しい設定作業を指す略称であり、切り替えるスイッチではありません。

### 1つのアプリをデプロイしたいだけでも、プラットフォームは必要ですか？

いいえ、そしておそらく構築すべきではありません。個人プロジェクトではCloudflareへ直接デプロイするのが正しい選択です。Void Platformチャレンジモードは、複数の開発者が共有アクセス、一貫したサインイン、デプロイ履歴を必要とする場合にのみ意味があります。

### インストール後にユーザーダッシュボードがないのはなぜですか？

標準インストールには含まれないからです。コアインストールはサンドボックスとメールゲートウェイを対象とし、ユーザーダッシュボード、マネージドGitHubビルドとウェブフック、ビルドコンテナ、カスタムプロジェクトドメインは別途追加するものです。ベースプラットフォームと一緒に付いてくると仮定せず、明示的に計画してください。

### Void Platformチャレンジモードで最もよくある間違いは何ですか？

CLIを誤ったURLに向けること、またはすべてのログイン方法を無効のままにすることです。どちらも、プラットフォーム自体は正常に動作しているのに、開発者からは「何も動かない」という同じ報告を生みます。誰かを招待する前に、URLと少なくとも1つの有効なログイン方法を確認してください。
