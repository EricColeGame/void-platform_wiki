## 「Void Platformダウンロード」の本当の意味

Void Platformのダウンロードを検索するほとんどの人は、単一のインストーラーファイルと「次へ次へ完了」のウィザードを期待しています。現実は異なります。Voidはチームが共有のCloudflareアカウントにデプロイするセルフホスト型プラットフォームであり、「ダウンロード」ステップは実際にはプラットフォームのツール一式を整えてセットアップフローを実行することです。この違いを最初に理解しておけば数時間を節約できます。なぜなら、そもそもプラットフォームが必要かどうかを決めることになるからです。自分自身のためだけにアプリをリリースするなら、Cloudflareに直接デプロイしてプラットフォームを完全に省略できます。

Voidプラットフォームは、開発者とCloudflareの間にある共有レイヤーです。管理者として、あなたがそれをインストールし、稼働させ続けます。その後、開発者はVoid CLIをプラットフォームのURLに向け、有効化されたログイン方法のいずれかでサインインし、その共有アカウントにアプリをデプロイします。Void Platformのダウンロードプロセスのあらゆる部分は、その引き継ぎを確実で再現可能にするために存在します。

プラットフォームはノートPC上ではなくあなたのCloudflareアカウント内に存在するため、ダウンロードはファイルというよりもインフラストラクチャに関するものです。Cloudflareの認証情報、プラン要件、文書化された一連のサービスを扱うことになります。以下の表で期待値を正しく整理しましょう。

| Void Platformのダウンロードに期待されること | 実際に起こること |
| --- | --- |
| 単一の`.exe`または`.dmg`インストーラー | プラットフォームはあなた自身のCloudflareアカウントにビルドおよびデプロイされる |
| ノートPC上で動作する | クラウド上で動作し、チーム全体で共有される |
| 即座に、アカウント設定不要 | Cloudflareの認証情報、Workers Paidプラン、文書化されたインフラストラクチャが必要 |
| すべてのプロジェクトに必須 | ソロ開発者は代わりにCloudflareに直接デプロイできる |
| すべてが箱から出して揃っている | コアインストールは意図的に最小限。アドオンは別途 |

## 前提条件と認証情報のチェックリスト

Void Platformのダウンロードを始める前に、必要なアカウントとアクセス権を集めましょう。実際には、失敗するインストールのほとんどは権限の欠如やプランのプロビジョニング不足が原因で、プラットフォーム自体の問題ではありません。まずこのリストを確認することで、イライラする午後がスムーズなセットアップに変わります。

| 要件 | 必要な理由 | 備考 |
| --- | --- | --- |
| Cloudflareアカウント | プラットフォームとデプロイされたすべてのアプリをホストする | チーム全体で共有 |
| Workers Paidプラン | マネージドSandboxesに必要 | プラットフォームアカウントに適用 |
| Workers for Platforms | チームプラットフォームに必要 | 文書化されたインフラストラクチャと組み合わせる |
| プラットフォームの認証情報 | インストールとAPIアクセスを認証する | 公式インストールガイドで説明されている |
| 共有メールドメインとゾーン | メールゲートウェイを有効にする | オプション — 設定するまでメールはオフのまま |
| Void CLI | 開発者が接続してデプロイする方法 | 各開発者のマシンにインストール |

このうち2つは特に注意が必要です。第一に、Workers Paidプランは個々の開発者のアカウントではなく、プラットフォームアカウントで有効になっている必要があります。そうでなければSandboxesは動作しません。第二に、認証情報は初日から本番のシークレットとして扱うべきです。なぜなら、インストールゲートウェイとプロキシは、プラットフォーム上のすべてのアプリのWorkers AIおよびプロバイダーへのリクエストの前に位置するからです。

組織がAPIを保護するためにCloudflare Accessを使用している場合は、Webhookのパスを早めに計画しましょう。オプションのGitHubサービスを追加するソースからビルドされたプラットフォームでは、受信WebhookがAccessによってブロックされないよう、分離されたWebhookイングレスが必要です。後からそれを追加するのは、最初から設計するよりもはるかに苦労します。

## コアインストールとオプションサービス

Void Platformのダウンロード後に最大の驚きの一つは、標準インストールに何が含まれ、何が意図的に除外されているかを発見することです。コアは設計上最小限です。マネージドSandboxesとメールゲートウェイで、メールは共有メールドメインとゾーンを設定して初めて有効になります。

| コアインストールに含まれるもの | コアインストールに含まれないもの |
| --- | --- |
| マネージドSandboxes | ユーザーダッシュボード |
| メールゲートウェイ（ドメインとゾーンの設定後） | GitHubビルドとWebhook |
| チームの共有アクセス | Build Containers |
| 保持されたデプロイ履歴 | カスタムプロジェクトドメイン |
| AIリクエスト用のインストールゲートウェイとプロキシ | あらゆる種類のマネージドGitHub連携 |

この区分はロールアウトを計画する際に重要です。初日から洗練されたダッシュボードを期待するチームは、誰かがそれを構築または追加しない限り失望するでしょう。同様に、GitHub駆動のビルドに依存するチームはオプションサービスレイヤーが必要であり、ブランド化されたプロジェクトドメインを望むチームはその作業を別途計画する必要があります。

実用的なアプローチは、まずコアをインストールし、Sandboxesとデプロイが動作することを確認してから、追加機能を重ねることです。各アドオンはメンテナンスする領域を増やし、壊れたオプションサービスはコアが正常であることがわかっていればはるかに診断が容易です。

## Cloudflare直接とセルフホスト型プラットフォーム

Void Platformのダウンロードを決める前に、プラットフォームが正しいターゲットであることを確認しましょう。どちらのパスも同じアプリケーションAPIを使用するため、どちらにもロックインされません。違いは共有アクセスと保持された履歴です。

| 機能 | Cloudflare直接 | コアセルフホスト型プラットフォーム |
| --- | --- | --- |
| Workers AIとプロバイダーリクエスト | あなたのアカウントとあなたのゲートウェイ | インストールゲートウェイとプロキシ |
| ランタイムログ | ライブCloudflare tail | 保持されたプラットフォームログ |
| アプリケーションのロールバック | Workerバージョン | 保持されたプラットフォームデプロイ |
| Sandboxes | Workers PaidとDockerが必要 | プラットフォームアカウントでWorkers Paidが必要 |
| ユーザーダッシュボードとマネージドGitHubビルド | 不要 | 標準インストールには含まれない |

簡単に言えば、自分用のアプリをデプロイして本番への最短経路を望むなら直接を選びましょう。チームが共有のデプロイターゲット、保持されたログ、生のWorkerバージョンではなく特定の保持されたデプロイへのロールバック機能を必要とするならプラットフォームを選びましょう。Sandboxesの違いにも注意してください。直接デプロイはローカルにDockerが必要ですが、プラットフォームはその要件をプラットフォームアカウントに押し付けます。

## ステップバイステップ：Void Platformのダウンロードから初回デプロイまで

前提条件が確認できたら、インストール自体は予測可能な順序に従います。各ステップをゲートとして扱いましょう。前のステップが検証されるまで次に進まないでください。

| ステップ | やること | 「完了」の状態 |
| --- | --- | --- |
| 1 | ターゲットを確認：Cloudflare直接かセルフホスト型プラットフォームか | 明確な決定をチームのために文書化 |
| 2 | Cloudflareアカウント、プラン、認証情報を準備する | Workers Paidが有効。チームセットアップ用にWorkers for Platformsを準備 |
| 3 | 公式インストールガイドを使ってプラットフォームをビルドおよびデプロイする | プラットフォームがそのURLで到達可能 |
| 4 | 共有メールドメインとゾーンを設定する（オプション） | メールゲートウェイが有効で送信中 |
| 5 | GitHubビルドやBuild Containersなどのオプションサービスを追加する | 各アドオンを個別に検証 |
| 6 | Void CLIを通じて開発者を接続する | 開発者がサインインしてテストアプリをリリース |

**ステップ1と2：決定とプロビジョニング。** 何かに触れる前に、直接実行するのかセルフホスト型を実行するのかを書き留めましょう。次にCloudflareアカウントをプロビジョニングし、Workers Paidプランを確認し、プラットフォームがチーム用であればWorkers for Platformsをセットアップします。認証情報はチャットでやり取りするのではなく、共有のシークレットストアに保管しましょう。

**ステップ3と4：インストールとメール設定。** 文書化されたインフラストラクチャが重要なので、場当たり的に進めるのではなく、公式の[Voidセルフホスト型プラットフォームインストールガイド](https://void.cloud/guide/self-hosted-platform)に従いましょう。プラットフォームに到達できたら、メールゲートウェイが必要なら共有メールドメインとゾーンを設定します。そのステップがなければ、メールは単に無効のままです。

**ステップ5と6：拡張とオンボーディング。** オプションサービスを一度に一つずつ追加し、それぞれの後にテストします。次に開発者にプラットフォームのURLとCLIの指示を渡し、チーム全体にプラットフォームを告知する前に、一人が完全なサインインとデプロイをスモークテストとして完了するようにします。

| 症状 | 考えられる原因 | 修正方法 |
| --- | --- | --- |
| Sandboxesが起動しない | プラットフォームアカウントでWorkers Paidが有効でない | そのアカウントのプランを確認またはアップグレード |
| 開発者がサインインできない | ログイン方法が有効化されていない | プラットフォーム設定でサポートされているログイン方法を有効化 |
| メールが送信されない | 共有メールドメインまたはゾーンが欠けている | ドメインとゾーンを設定してから再テスト |
| Access背後のGitHub Webhookが失敗する | Webhookイングレスが分離されていない | 分離されたWebhookイングレスのセットアップに従う |
| チーム機能が利用できない | Workers for Platformsが設定されていない | 文書化されたインフラストラクチャを完了する |

## よくある質問

**WindowsやmacOS用のVoid Platformダウンロードはありますか？**
いいえ、コンシューマー向けのデスクトップインストーラーはありません。Void Platformのダウンロードとは、プラットフォームをあなた自身のCloudflareアカウントにビルドしてデプロイすることを意味します。ローカルマシンには、開発者がプラットフォームのURLに接続してデプロイできるよう、Void CLIだけが必要です。

**ソロ開発者ならVoid Platformのダウンロードは必要ですか？**
通常は不要です。自分用のアプリをデプロイするなら、Cloudflareに直接デプロイしてプラットフォームを省略しましょう。プラットフォームは、チームが共有のデプロイターゲット、保持されたログ、ロールバック用の保持されたデプロイ履歴を必要とするときにその価値を発揮します。

**標準インストールから欠けているものは何ですか？**
ユーザーダッシュボード、GitHubビルドとWebhook、Build Containers、カスタムプロジェクトドメインはすべてコアインストールの対象外です。マネージドSandboxesとメールゲートウェイは含まれますが、メールは共有メールドメインとゾーンが設定されて初めて機能します。

**チームプラットフォームにはどのプランが必要ですか？**
チームプラットフォームにはWorkers for Platformsと文書化されたインフラストラクチャが必要で、マネージドSandboxesにはプラットフォームアカウントでのWorkers Paidプランが必要です。正確な機能はインストールの設定方法によって異なるため、開始前に公式ガイドを確認してください。
