## Void Platformとは何か — そしてボイドサバイバルが重要な理由

ほとんどのチームはアプリの出荷に失敗するのではなく、出荷を支える共有基盤を生かし続けることに失敗します。そこが**Void Platformのボイドサバイバル**の実践的な核心です。つまり、セルフホスト型プラットフォームをインストールし、保守し、トラブルシューティングすることで、開発者が問題なくデプロイを続けられるようにすることです。管理者が1人インストールを所有し、それ以外の全員がVoid CLIを通じて接続し、共有のCloudflareアカウントにアプリをプッシュします。

そのプラットフォームが停止すると、下流の開発者は全員足止めされます。このガイドでは**Void Platformのボイドサバイバル**の仕組みを分解して解説します。コアインストールに含まれるもの、意図的に含まれないもの、そしてデプロイを復旧可能な状態に保つ方法です。

Void Platformは、チームが1つの共有Cloudflareアカウントにアプリをデプロイできるようにするセルフホスト型のコントロールプレーンです。管理者がプラットフォームをインストールして保守し、開発者はVoid CLIをプラットフォームのURLに接続し、有効化されたログイン方法でサインインしてアプリをデプロイします。デプロイの流れは開発者ごとに変わりません。まさにそこが要点です。

代替案は、全員が自分のCloudflareアカウント、自分のログ、自分のロールバック履歴を管理することです。個人開発者ならそれで問題ありません。しかし3人が同じデプロイ履歴を見る必要が出た瞬間に破綻します。

| 役割 | 所有するもの | 日常的に触るもの |
| --- | --- | --- |
| プラットフォーム管理者 | インストール、保守、ログイン方法、共有メールドメインとゾーン | 保持されたログ、デプロイ履歴、ゲートウェイ設定 |
| 開発者 | 自分のアプリとそのデプロイ | Void CLIのサインイン、デプロイコマンド、ランタイムログ |
| チームオーナー | アクセスポリシーとプラン状況 | 誰がアカウントを持つか、Workers Paidが有効かどうか |

Void Platformのボイドサバイバルは、最初のインストールよりも2か月目に関わってきます。インストールはチェックリストです。2か月目こそが、共有アクセス、保持された履歴、ロールバックが本当に価値を発揮する場面です。

## 直接Cloudflare vs. コアのセルフホスト型プラットフォーム

どちらのデプロイ先も同じアプリケーションAPIを使うため、プラットフォームは別製品ではなく、別の運用モデルです。コアプラットフォームは、Cloudflareがすでに提供しているものの上に、共有アクセスと保持されたデプロイ履歴を追加します。

| 機能 | Cloudflareへ直接 | コアのセルフホスト型プラットフォーム |
| --- | --- | --- |
| Workers AIとプロバイダーリクエスト | 自分のアカウントと自分のゲートウェイ | インストールのゲートウェイとプロキシ |
| ランタイムログ | ライブのCloudflare tail | 保持されたプラットフォームログ |
| アプリケーションのロールバック | Workerのバージョン | 保持されたプラットフォームのデプロイ |
| Sandboxes | Workers PaidとDockerが必要 | プラットフォームアカウントでWorkers Paidが必要 |
| ユーザーダッシュボードと管理されたGitHubビルド | 不要 | 標準インストールには含まれない |

この表はトレードオフとして読んでください。直接デプロイはハードウェアに近い状態を保てます。可動部分が少なく、保守すべき共有面がなく、他の誰かを壊すものもありません。セルフホスト型プラットフォームは記憶を与えてくれます。ブラウザタブより長生きするログと、現在のWorkerバージョンを超えて残るデプロイ記録です。

その記憶こそがVoid Platformのボイドサバイバルの要点です。ライブtailは閉じた瞬間に消えます。保持されたログエントリは、翌朝に誰かが「前回のリリースが妙な挙動をしたのはなぜか」と尋ねたときにもまだそこにあります。

### 直接デプロイが正解となる場合

自分のためにアプリをデプロイするなら、Cloudflareへ直接デプロイしてください。まずプラットフォームをインストールする必要はなく、立ち上げても個人開発者では回収できない保守作業が増えるだけです。

プラットフォームが元を取れるようになるのは、作者以外の誰かがデプロイし、履歴を確認し、ロールバックする必要が出たときです。そこが注目すべき閾値です。

## コアインストールの中身：含まれるものと含まれないもの

コミュニティ報告で最も混乱を招くのは、「プラットフォームをインストールした」と「すべてをインストールした」の間のギャップです。コアインストールは意図的に狭く作られています。

| コンポーネント | コアインストールでの状態 | あなたにとっての意味 |
| --- | --- | --- |
| マネージドSandboxes | 含まれる | プラットフォームアカウントでWorkers Paidが必要 |
| メールゲートウェイ | 含まれる（条件付き） | 共有メールドメインとゾーンを設定すると有効化 |
| ユーザーダッシュボード | 含まれない | CLIファーストのワークフローを想定 |
| GitHubビルドとwebhook | 含まれない | ソースビルド型プラットフォームではオプション |
| ビルドContainers | 含まれない | 標準インストールの一部ではない |
| カスタムプロジェクトドメイン | 含まれない | プラットフォーム提供のホスト名を想定 |
| Workers for Platforms | チームプラットフォームには必須 | 文書化されたインフラ要件を伴う |

2つの詳細に注意が必要です。第一に、メールはプラットフォームをインストールしただけでは有効になりません。共有メールドメインとゾーンを設定した時点で有効化されます。第二に、ソースからビルドしてオプションのGitHubサービスを追加する場合、AccessがAPIを保護しているときは分離されたwebhook ingressの設定に従ってください。このステップを飛ばすのは、他のすべてが正常に見えるままwebhook配信を壊す典型的な原因です。

| インストール種別 | 最適な用途 | 注意点 |
| --- | --- | --- |
| コアインストール | 共有アクセスと保持された履歴を求めるチーム | ダッシュボードなし、管理されたGitHubビルドなし |
| オプションサービス付きソースビルド | GitHub連携が必要なチーム | APIの前にAccessがある場合の分離されたwebhook ingress |

## Void Platformのインストール：実践チェックリスト

インストールは順序であり、速度よりも順番が重要です。[公式のVoidセルフホスト型プラットフォームインストールガイド](https://void.cloud/guide/self-hosted-platform)とこのチェックリストを併用して進めてください。

| ステップ | アクション | 次に進む前のサバイバルチェック |
| --- | --- | --- |
| 1 | 前提条件を確認 | プラットフォームアカウントに必要なプランを把握している |
| 2 | 認証情報を準備 | 管理者アクセスが1人の頭だけでなく文書化されている |
| 3 | プラットフォームアカウントをプロビジョニング | Sandboxesを使うならWorkers Paidが有効 |
| 4 | ログイン方法を選択 | 少なくとも2人がサインインできる |
| 5 | 共有メールドメインとゾーンを設定 | メールゲートウェイが有効と表示される |
| 6 | コアプラットフォームをインストール | テストデプロイが成功する |
| 7 | CLIを接続 | インストールしていない開発者がデプロイできる |
| 8 | ログとロールバックを検証 | 昨日のデプロイを見つけて戻せる |

ステップ7はチームが飛ばしがちな項目です。管理者がデプロイに成功して勝利を宣言し、1週間後に他の誰も認証できないことに気づきます。プラットフォームを告知する前に、2人目にCLI接続、サインイン、デプロイの全フローを実行してもらいましょう。

ステップ8ももう1つの静かな失敗です。保持されたログと保持されたデプロイは、それを見つける練習をして初めて役に立ちます。リスクが低い間に、意図的に一度ロールバックをやってみてください。

チーム向けには、プラットフォームはWorkers for Platformsとその周辺の文書化されたインフラも必要とします。誰かに共有環境を約束する前に、[Cloudflare Workers for Platformsのドキュメント](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/)を必読資料として扱ってください。

## チーム向けVoid Platformボイドサバイバルのヒント

プラットフォームが稼働したら、サバイバルはプロジェクトではなく保守の習慣になります。長持ちするパターンを紹介します。

| リスク | 緩和策 |
| --- | --- |
| 管理者が退職または不在になる | ログイン方法を文書化し、管理者業務を分担する |
| ライブtailの習慣が残る | 保持されたプラットフォームログを読むよう開発者を教育する |
| ロールバックが未検証 | 四半期に1回ロールバックを練習する |
| Sandboxesが動かなくなる | プラットフォームアカウントでWorkers Paidを有効に保つ |
| Accessの背後でwebhookが失敗する | オプションのGitHubサービスには分離されたwebhook ingressを使う |
| メールが静かに欠落する | 共有メールドメインとゾーンの設定を再確認する |

- **プロバイダーリクエストをインストールのゲートウェイ経由にする。** Workers AIとプロバイダー呼び出しを集中化することで、認証情報を個々の開発者マシンから遠ざけられます。
- **デプロイ履歴をドキュメントとして扱う。** 保持されたデプロイ記録は、どんなチャットスレッドよりも速く「何が変わったか」に答えます。
- **コアインストールはコアのままに。** オプションサービスを追加するのは構いませんが、追加のたびにVoid Platformのボイドサバイバル訓練中に壊れうるものが増えます。
- **プラットフォームの変更とアプリの変更を分ける。** デプロイがおかしくなったとき、プラットフォームとアプリのどちらが先に動いたか分かれば数時間節約できます。
- **プラン変更後に設定を見直す。** Sandboxesやチーム機能は、自分の下で変わりうるプランとインフラの状態に依存します。

これらすべてを貫くテーマは可視性です。コアプラットフォームが追加するすべての機能（ゲートウェイルーティング、保持されたログ、保持されたデプロイ）は、問題を謎ではなく観測可能にするために存在します。Void Platformのボイドサバイバルに本気で取り組むチームは、可観測性をボーナスではなく製品そのものとして扱います。

コミュニティの報告も同じことを伝えています。インストールは週末で終わりますが、6か月後もプラットフォームが信頼されているかどうかを決めるのは運用の習慣です。

## FAQ

**CloudflareにアプリをデプロイするのにVoid Platformは必要ですか？**
いいえ。自分のためにアプリをデプロイするならCloudflareへ直接デプロイしてください。まずプラットフォームをインストールする必要はありません。プラットフォームは、チームが共有アクセスと保持されたデプロイ履歴を必要とするときに意味を持ちます。

**コアインストールには実際何が含まれますか？**
マネージドSandboxesとメールゲートウェイで、メールは共有メールドメインとゾーンを設定した時点でのみ有効になります。ユーザーダッシュボード、GitHubビルドとwebhook、ビルドContainers、カスタムプロジェクトドメインはコアインストールには含まれません。

**Void Platformのボイドサバイバルにおいて、保持されたログが重要なのはなぜですか？**
ライブのCloudflare tailは閉じると消えるからです。保持されたプラットフォームログと保持されたデプロイは後から検査できる記録を与え、それが障害を診断へと変えます。

**Sandboxesにはどのプランが必要ですか？**
プラットフォームアカウントのWorkers Paidです。Cloudflareへ直接の経路では、代わりに自分のマシンでWorkers PaidとDockerが必要です。
