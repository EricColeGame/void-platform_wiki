## Void Platform プラットフォームチャレンジの実際の内容

チーム向けの共有インフラを構築する作業が単一のコマンドで済むことはほとんどなく、**Void Platform プラットフォームチャレンジ**の本質は、各要素を正しい順序で進めることにあります。順序さえ正しければ、開発者は Void CLI を URL に向け、サインインし、共有の Cloudflare アカウントにアプリをデプロイできます。順序を誤ると、認証情報と中途半端に設定されたサービスの整理に午後を丸ごと費やすことになります。

このガイドでは、**Void Platform プラットフォームチャレンジ**を最初から最後まで解説します。誰が何を担当するのか、どの要件がインストールの前提条件になるのか、そして標準インストールでは意図的に省かれる機能にどう備えるのかを見ていきます。

最初の判断は、そもそもプラットフォームが必要かどうかです。Void プラットフォームは共有のデプロイ先であり、1 つの Cloudflare アカウント、1 つのプラットフォーム URL、多数の開発者という構成です。管理者がインストールと保守を行います。開発者は Void CLI をその URL に接続し、有効化されたログイン方法で認証してデプロイします。自分自身のためだけにアプリをデプロイする場合は、プラットフォームを完全に省略し、Cloudflare に直接デプロイしてください。

役割は単純ですが、これを混同することが初期段階で最もよくある間違いです：

| 役割 | 担当範囲 | 使用するツール |
| --- | --- | --- |
| 管理者 | プラットフォームのインストール、保守、設定。共有 Cloudflare アカウントの管理 | プラットフォームのインストール |
| 開発者 | CLI の接続、サインイン、アプリのデプロイ | Void CLI |
| ソロ開発者 | 共有レイヤーなしでアプリをリリース | Cloudflare への直接デプロイ |

コアインストールには、管理された Sandboxes とメールゲートウェイが含まれます。メール機能は、共有メールドメインとゾーンを設定したときにのみ有効になるため、メールが最初から動作する前提にせず、その手順を計画してください。

## Cloudflare への直接デプロイとコアのセルフホスト型プラットフォーム

どちらのデプロイ先も同じアプリケーション API を使用するため、一方から他方へ移行するときにアプリを書き直す必要はありません。変わるのはアプリの周辺すべてです。共有アクセス、保持されるデプロイ履歴、リクエストのルーティング方法が異なります。

| 機能 | Cloudflare への直接デプロイ | コアのセルフホスト型プラットフォーム |
| --- | --- | --- |
| Workers AI とプロバイダーリクエスト | 自分のアカウントとゲートウェイ | インストールのゲートウェイとプロキシ |
| ランタイムログ | Cloudflare のライブテール | プラットフォームに保持されるログ |
| アプリケーションのロールバック | Worker のバージョン | プラットフォームに保持されるデプロイ |
| Sandboxes | Workers Paid と Docker が必要 | プラットフォームアカウントで Workers Paid が必要 |
| ユーザーダッシュボードと管理された GitHub ビルド | 不要 | 標準インストールには含まれない |

この表が **Void Platform プラットフォームチャレンジ**の核心です。プラットフォームはデプロイを可能にするのではなく、デプロイを*共有可能で復旧可能*にします。ライブテールと Worker のバージョンは 1 人で使うには十分です。保持されたログと保持されたプラットフォームデプロイがあれば、チームは翌朝にインシデントを調査し、推測に頼らずロールバックできます。

数人の同僚ではなくチームのために運用する場合は、より大きな構成を想定してください。チームプラットフォームには Workers for Platforms と文書化されたインフラが必要です。機能はインストールの設定方法によって異なるため、選択内容は後任者が見つけられる場所に記録してください。

## 前提条件と認証情報：最初のハードルをクリアする

インストールの失敗の多くは、インストールが始まる前に起きます。前提条件のページと認証情報のページを最後まで読み、すべてを 1 か所に集めてから始めてください。[Void セルフホスト型プラットフォームの公式インストールガイド](https://void.cloud/guide/self-hosted-platform) がここでの信頼できる情報源です。短い内容なので、流し読みするほうがむしろ時間を浪費します。

| 要件 | 有効になるもの | 必要なタイミング |
| --- | --- | --- |
| プラットフォームアカウントの Workers Paid | 管理された Sandboxes | Sandbox に依存するアプリを公開する前 |
| Workers for Platforms と文書化されたインフラ | チームプラットフォーム | ソロ構成ではなくチームに提供する場合のみ |
| 有効化されたログイン方法 | CLI を通じた開発者のサインイン | プラットフォーム URL を配布する前 |
| 共有メールドメインとゾーン | メールゲートウェイ | アプリがメールを送信する場合のみ |
| 収集済みの認証情報 | インストール自体 | 最初のステップの前 |

実際に時間を節約できる 3 つのヒント：

- **ログイン方法を最初に決める。** 初日に開発者へ伝える内容がこれで決まり、後から変更すると全員のオンボーディングをやり直すことになります。
- **共有 Cloudflare アカウントを本番環境として扱う。** プラットフォーム上のすべての開発者が、その制限と影響範囲を引き継ぎます。
- **プラットフォーム URL を書き留める。** すべての開発者が必要とする唯一の情報であり、最もよくチャットスレッドに埋もれてしまう情報です。

## Void Platform プラットフォームチャレンジをステップバイステップで進める

前提条件が揃っていれば、インストール自体は短い工程です。**Void Platform プラットフォームチャレンジ**の大部分は、その周辺のステップにあります。

| ステップ | アクション | 完了条件 |
| --- | --- | --- |
| 1 | 対象を確認する：Cloudflare への直接デプロイか、セルフホスト型プラットフォームか | チームにプラットフォームの必要性を説明できる |
| 2 | 前提条件と認証情報を確認する | すべての認証情報が揃っている |
| 3 | コアプラットフォームをインストールする | 管理された Sandboxes とメールゲートウェイが存在する |
| 4 | ログイン方法を有効化する | 開発者が認証できる |
| 5 | 共有メールドメインとゾーンを設定する | メールが実際に有効になっている |
| 6 | URL を共有し、テストデプロイを実行する | 1 人の開発者がアプリを正常にリリースできる |
| 7 | オプションサービスを意図的に追加する | 各追加項目に担当者がいる |

開発者から問題が報告された場合は、再インストールするのではなく、症状から逆算して原因を追ってください：

| 症状 | 考えられる原因 | 最初に確認する項目 |
| --- | --- | --- |
| 開発者がサインインできない | ログイン方法が有効化されていない、または CLI が誤った URL を指している | プラットフォーム URL と有効化されたログイン方法 |
| メールが送信されない | 共有メールドメインとゾーンが設定されていない | メールドメインとゾーンの設定 |
| Sandboxes が起動しない | プラットフォームアカウントに Workers Paid がない | プラットフォームアカウントのプラン |
| Access の背後で GitHub Webhook が失敗する | Webhook のイングレスが分離されていない | 分離された Webhook イングレスの設定 |

最後の行は見た目以上に重要です。オプションの GitHub サービスを追加するソースビルド型プラットフォームでは、Access が API を保護している場合、分離された Webhook イングレスの設定に従う必要があります。そうしないと、API を安全に保つ保護によって Webhook 自体がブロックされます。

## コアインストールで省かれる機能に備える

標準インストールは意図的に最小構成です。何が含まれないかを把握しておけば、存在しない機能に対してバグ報告することを避けられます：

| 機能 | コアインストールに含まれるか | 計画すべきタイミング |
| --- | --- | --- |
| 管理された Sandboxes | はい | アプリにサンドボックス実行が必要ならすぐに |
| メールゲートウェイ | はい（設定後） | アプリがトランザクションメールを送信するとき |
| ユーザーダッシュボード | いいえ | CLI のみのワークフローではなく UI が必要なとき |
| GitHub ビルドと Webhook | いいえ | プッシュツーデプロイが必要なとき |
| Build Containers | いいえ | ビルドにコンテナ化された環境が必要なとき |
| カスタムプロジェクトドメイン | いいえ | アプリに独自のホスト名が必要なとき |

ここが **Void Platform プラットフォームチャレンジ**における分岐点であり、チームによって選択が分かれます。コアインストールのまま無期限に運用し、すべてを CLI で進めるチームもあれば、GitHub サービスを追加するためにソースからビルドするチームもあります。後者の場合、Webhook イングレスの問題が再び浮上します。どちらの道も間違いではありませんが、ローンチ中に不足に気づくより、意図的に決めておくほうが優れています。

ここでは 2 つの実践的な習慣が役立ちます。まず、インストールに含まれる内容を短い一覧として書き留めておくことです。「機能は設定に依存する」と言うのは簡単ですが、半年後に思い出すのは難しいからです。次に、オプションサービスを追加するときは、誰が担当し、どのようにテストするかを記録することです。担当者のいないオプションサービスは、静かに劣化していく傾向があります。

## よくある質問

**自分だけでデプロイする場合でも、Void Platform プラットフォームチャレンジに取り組む必要がありますか？**  
いいえ。自分自身のためにアプリをデプロイする場合は、Cloudflare に直接デプロイしてください。プラットフォームを先にインストールしたり保守したりすることなく、同じアプリケーション API を利用できます。

**コアインストールには実際に何が含まれますか？**  
管理された Sandboxes とメールゲートウェイです。メールは、共有メールドメインとゾーンを設定したときに有効になります。ユーザーダッシュボード、GitHub ビルドと Webhook、Build Containers、カスタムプロジェクトドメインはコアインストールには含まれません。

**GitHub ビルドを後から追加できますか？**  
はい。ただし、コアインストールではなく、ソースからビルドしたプラットフォームを実行する必要があります。Access が API を保護している場合は、Webhook が引き続きプラットフォームに到達できるよう、分離された Webhook イングレスの設定に従ってください。

**Void Platform プラットフォームチャレンジで最もよくある間違いは何ですか？**  
インストールだけの作業として捉えてしまうことです。インストールは短時間で終わります。ログイン方法、メール設定、オプションサービス、そして各要素の担当者を中心とした計画こそが、プラットフォームが安定して運用できるかを決めます。
