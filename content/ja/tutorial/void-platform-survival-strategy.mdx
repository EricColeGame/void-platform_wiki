## Void Platform サバイバル戦略がインストール前に始まる理由

Void プラットフォームは、共有の Cloudflare アカウントをチーム全体が使えるデプロイ先に変えます。そして、あらゆる共有インフラと同じく、誰かがその維持を計画しなければ有用なままではいられません。本当の Void Platform サバイバル戦略とは、障害時のヒロイックな対応ではなく、初日に下す地味な判断——どの機能をインストールし、何を監視し、どれだけ早く既知の正常なデプロイに戻れるか——のことです。

その計画がなければ、1人の開発者には問題なく機能する構成が、10人にとっては静かに負債になります。このガイドでは、Void Platform サバイバル戦略の実践面を、適切なデプロイ先の選び方から、ログ・ロールバック・サンドボックスを本当に必要なときに使える状態に保つメンテナンスの計画まで順を追って説明します。

## まず適切なターゲットを選ぶ：Cloudflare 直接か、共有プラットフォームか

最大のサバイバル判断はインストール前に下されます。自分用のアプリをデプロイするなら、Cloudflare に直接デプロイし、プラットフォームは完全に省きます。プラットフォームは、チーム向けの共有アクセスと保持されたデプロイ履歴を追加するために存在します。

どちらの道も同じアプリケーション API を使うため、違いは技術的ではなく運用上のものです。必要のないプラットフォームを構築すると、失敗しうる可動部品が増えます。チームがいるのにプラットフォームを省くと、復旧を可能にするセーフティネットが失われます。

| 機能 | Cloudflare への直接デプロイ | コアのセルフホスト型 Void プラットフォーム |
| --- | --- | --- |
| Workers AI とプロバイダーへのリクエスト | 自分のアカウントと自分のゲートウェイ | インストールのゲートウェイとプロキシ経由でルーティング |
| ランタイムログ | Cloudflare からのライブテイル | プラットフォーム上にログを保持 |
| アプリケーションのロールバック | Worker のバージョン履歴 | 保持されたプラットフォームのデプロイ |
| サンドボックス | Workers Paid と Docker が必要 | プラットフォームアカウントでの Workers Paid が必要 |
| ユーザーダッシュボードとマネージド GitHub ビルド | 不要 | 標準インストールには含まれない |
| チームでの共有アクセス | 提供されない | 標準搭載 |

簡単な目安：デプロイする人が2人以上いる場合、あるいは「先週の火曜日に何を出荷したっけ？」と一度でも尋ねたことがあるなら、共有プラットフォームはそのコストに見合います。

## コアインストールが何を提供し、何を提供しないかを正確に把握する

自分で招く障害のほとんどは、含まれていない機能が含まれていると思い込むことから生じます。コアインストールは意図的に最小限で、マネージドサンドボックスとメールゲートウェイを提供します。メールは共有メールドメインとゾーンを設定して初めて機能します。それまではゲートウェイは存在しても、送信元がありません。

ユーザーダッシュボード、GitHub ビルドと Webhook、ビルドコンテナ、カスタムプロジェクトドメインはすべてコアインストールの外側です。スプリントの途中でギャップに気づくのではなく、それぞれを明示的に計画しましょう。

| コンポーネント | 標準インストールに含まれるか | 計画しない場合のサバイバルへの影響 |
| --- | --- | --- |
| マネージドサンドボックス | はい | 追加の配線なしでランタイム環境が利用可能 |
| メールゲートウェイ | はい（共有メールドメインとゾーンの設定後） | ゾーンが存在するまで通知はサイレントに失敗する |
| ユーザーダッシュボード | いいえ | 開発者は CLI と API のみに依存する |
| GitHub ビルドと Webhook | いいえ — オプション、ソースからのビルド | マージが自動デプロイされず、手動デプロイになる |
| ビルドコンテナ | いいえ | ビルドはプラットフォームの外で行う必要がある |
| カスタムプロジェクトドメイン | いいえ | 追加するまでアプリはデフォルトのホスト名で動作する |

ソースからプラットフォームを構築し、オプションの GitHub サービスを追加する場合、Cloudflare Access が API を保護しているときは必ず分離された Webhook イングレスの構成を使用してください。Access で保護された API と平文の Webhook エンドポイントを混在させることは、セキュリティ強化の実施後に稼働中のプラットフォームが壊れる最も一般的な原因の一つです。

## Void Platform サバイバル戦略の5つの柱

これらを耐荷重壁として扱ってください。それぞれが特定の障害モードに対応し、何かおかしいと感じたときに最初に確認すべき項目があります。

| 柱 | それがないと何が失敗するか | 最初に確認すること |
| --- | --- | --- |
| アイデンティティとアクセス | 開発者がサインインできない、さらに悪い場合は間違った人がサインインできる | プラットフォームでどのログイン方法が有効になっているか |
| デプロイ履歴 | 障害時にクリーンなロールバック先がない | 保持されたデプロイが実際に蓄積されているか |
| 可観測性 | 障害をログではなくユーザーから知ることになる | プラットフォームのログが保持され、読める状態か |
| ランタイム容量 | 負荷がかかるとサンドボックスが起動を拒否する | プラットフォームアカウントの Workers Paid の状況と Docker の可用性 |
| メール経路 | 招待、アラート、リセットが決して届かない | 共有メールドメインとゾーンの設定 |

**アクセス。** すべての開発者は Void CLI をプラットフォーム URL に接続し、有効化されたログイン方法でサインインします。そのリストは短く最新に保ってください。退職した同僚のログインが有効なままなのは、人事の問題ではなくサバイバルの問題です。

**履歴。** 保持されたデプロイが復旧の仕組みです。ロールバック履歴のないプラットフォームは、プレッシャーの中でソースから再構築することを強いられます。まさにそこでミスが積み重なります。

**可観測性。** ライブテイルはデバッグ中は有用ですが、事後には役に立ちません。保持されたプラットフォームログこそが、翌朝に障害を再構成できるようにします。

**容量。** サンドボックスにはプラットフォームアカウントでの Workers Paid が必要で、Cloudflare 直接のサンドボックスにはさらに Docker が必要です。ローンチの前に権利を確認し、ローンチ中に確認しないようにしましょう。

**メール。** 共有ドメインとゾーンが設定されるまで、メールゲートウェイは何も機能しません。インストール日に済ませて、障害時に DNS をデバッグする羽目にならないようにしましょう。

## 実際に続けられるメンテナンスの周期を決める

Void Platform サバイバル戦略が失敗するのは、悪いアーキテクチャよりも怠慢によることが最も多いです。小さく定期的なチェックは、たまの大掃除に勝ります。

| 周期 | タスク | 重要な理由 |
| --- | --- | --- |
| 週次 | CLI が接続でき、テストデプロイが成功することを確認 | 認証情報とログイン方法のずれを早期に捉える |
| 週次 | 保持されたログをざっと見て繰り返し発生するエラーを探す | 漠然とした不安定さを具体的な修正に変える |
| 月次 | 低リスクのアプリでロールバックが機能することを確認 | 一度もテストしていないロールバック経路は経路ではない |
| 月次 | サインインできる人を見直す | 古いアカウントの影響範囲を縮小する |
| 四半期 | インストールの前提条件と認証情報を再確認 | プラットフォームの進化に伴い設定要件は変わる |
| 変更後は毎回 | デプロイ、ログ、メールをエンドツーエンドで再テスト | 障害のほとんどはコード変更ではなく設定変更に続いて起きる |

四半期レビューは、ほとんどのチームが驚きを見つける場です。期限切れの認証情報、誰も有効化した覚えのないログイン方法、あるいは最後まで設定されなかったゾーンなどです。

## プラットフォームが不調なときのためのリスクマトリクス

この表をチームが見つけられる場所に置いておきましょう。すべてを診断できるわけではありませんが、障害発生から最初の10分を短縮します。

| 症状 | 想定される原因 | 最初の対応 |
| --- | --- | --- |
| CLI がプラットフォームに到達できない | URL が間違っている、または有効なログイン方法がない | プラットフォーム URL を確認し、次にログイン方法を確認する |
| デプロイは成功するがログがない | 見ている場所にログが保持されていない | ライブテイルではなくプラットフォームのログ保持を確認する |
| 最近のリリースにロールバック先がない | そのアプリのデプロイ履歴が保持されていない | 再構築する前に保持されたデプロイ一覧を調べる |
| サンドボックスが起動しない | Workers Paid がない、または Docker が利用できない | プラットフォームアカウントのプランを確認する |
| メールが決して届かない | 共有メールドメインまたはゾーンが未設定 | メールドメインとゾーンの設定を完了する |
| 強化後に GitHub Webhook が失敗する | 分離されたイングレスなしで Access が API を保護している | 分離された Webhook イングレスのパターンに移行する |

## スケールアップ：チームプラットフォームに実際に必要なもの

チームプラットフォームは個人インストールよりも大きなコミットメントです。Workers for Platforms と文書化されたインフラが必要で、正確な機能セットはインストールの構成方法によって異なります。開発者にダッシュボード、自動 GitHub ビルド、カスタムドメインを約束する前に、そのコストを見積もっておきましょう。

| 要件 | 対象 | サバイバル上の注意 |
| --- | --- | --- |
| Workers for Platforms | チームプラットフォーム | アドオンではなくコアインフラ |
| プラットフォームアカウントの Workers Paid | サンドボックス | 開発者のオンボーディング前に確認する |
| 文書化されたインフラ | チームプラットフォーム | 逸脱すると文書化されていない障害モードを生む |
| 分離された Webhook イングレス | Access 背後のオプションの GitHub サービス | Webhook のサイレント失敗を防ぐ |

公式の [Void プラットフォームインストールガイド](https://void.cloud/guide/self-hosted-platform) はブックマークしておくべきリファレンスです。前提条件と認証情報を扱っており、設定が文書化された道筋から外れたときの信頼できる情報源になります。

Void Platform サバイバル戦略の最も耐久性のある形は地味です。必要なものだけをインストールし、履歴とログを保持し、必要になる前にロールバックをテストし、定期的にアクセスを見直す。そうすれば、プラットフォームは障害発生装置ではなくデプロイツールのままでいられます。

## FAQ

**開発者が自分一人だけなら、プラットフォームをインストールする必要はありますか？**
いいえ。Cloudflare への直接デプロイは同じアプリケーション API を使い、プラットフォームのオーバーヘッドを完全に省きます。Void Platform サバイバル戦略が手間に見合うのは、チーム向けの共有アクセスと保持されたデプロイ履歴が必要になったときだけです。

**Void Platform サバイバル戦略で最速の復旧方法は何ですか？**
保持されたデプロイへのロールバックです。だからこそ低リスクのアプリで毎月ロールバックをテストすることが重要なのです。復旧経路は障害の最中ではなく、その前に機能していなければなりません。

**メールは標準インストールに含まれていますか？**
メールゲートウェイはコアインストールの一部ですが、共有メールドメインとゾーンを設定した後にしか機能しません。その設定はフォローアップのタスクではなく、インストールの一部として扱いましょう。

**Access を有効にした後、GitHub Webhook が壊れたのはなぜですか？**
Cloudflare Access が API を保護している場合、オプションの GitHub サービスには分離された Webhook イングレスの構成が必要です。それがないと Webhook 呼び出しがブロックされ、ビルドがトリガーされなくなります。誰かが「なぜ何もデプロイされないのか」と尋ねるまで気づきにくい障害です。
