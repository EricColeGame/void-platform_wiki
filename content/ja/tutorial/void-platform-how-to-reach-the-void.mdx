## 「Void に到達する」とは実際に何を意味するのか

Void Platform は、チーム全体が単一の Cloudflare アカウントにアプリをデプロイできるようにする共有レイヤーであり、Void に到達する方法を知っているかどうかが、最初のデプロイが5分で終わるか、午後を丸ごと無駄にするかの差になります。これまでにプラットフォームの URL と CLI を渡されて「つなぐだけ」と言われたことがあるなら、足りないのはコンテキストだということがすでにお分かりでしょう。このガイドでは Void Platform を扱います。インストールする管理者として、またサインインして CLI をリンクし、アプリを出荷する開発者として、Void に到達する方法を説明します。

「Void に到達する」という表現は曖昧に使われるため、3つの異なるレイヤーに分けると役立ちます。失敗のほとんどは、あるレイヤーを解決して、残り2つも処理済みだと思い込んだことが原因です。

| レイヤー | 実際の見え方 | 通常の担当者 |
| --- | --- | --- |
| ネットワーク到達性 | プラットフォームに、リクエストに応答する URL がある | 管理者 |
| 認証到達性 | 少なくとも1つのログイン方法が有効で、人間がサインインできる | 管理者 |
| ツール到達性 | Void CLI がその URL を指し、認証済みである | 開発者 |

どれか1つでも欠けていると、プラットフォームは存在していても実質的に到達不可能なままです。順番に解決してください。

## 始める前に: 前提条件とアクセス要件

Void プラットフォームは、単にログインするだけのホスト型サービスではありません。管理者がインストールして維持するものです。つまり、前提条件は、プラットフォームアカウントに必要なインフラストラクチャと、クライアント側に必要な認証情報にきれいに分かれます。

| 要件 | 重要な理由 | 備考 |
| --- | --- | --- |
| プラットフォーム用の Cloudflare アカウント | プラットフォームは共有アカウントにアプリをデプロイする | コアインストールは単一の共有アカウントを対象とする |
| プラットフォームアカウントの Workers Paid | マネージド Sandboxes に必要 | Sandboxes はコアインストールの一部 |
| Docker（直接デプロイの経路） | Sandboxes を自分で実行する場合、ローカルに必要 | 共有プラットフォームを利用するだけなら不要 |
| 共有メールドメインとゾーン | 設定するまでメールゲートウェイ機能はオフのまま | メールはドメインとゾーンを設定した後にのみ有効になる |
| 管理者認証情報 | プラットフォームのインストールと維持に必要 | 認証情報ガイドに記載 |
| 有効なログイン方法 | これがないと誰もサインインを完了できない | インストール中または直後に設定 |
| 各開発者マシンの Void CLI | 開発者がプラットフォームに到達する主な手段 | プラットフォーム URL に接続する |

始める前の実用的なヒント:

- ターミナルを触る前に、公式の [Void インストールドキュメント](https://void.cloud/guide/self-hosted-platform) にある前提条件と認証情報のガイドを読んでください。短く、ほとんどの手戻りを防げます。
- 単独のターゲットを構築するのか、チームプラットフォームを構築するのかを最初に決めてください。チームプラットフォームには Workers for Platforms と文書化されたインフラストラクチャが必要で、かなり大規模な構築になります。
- メールがワークフローにとって重要なら、DNS ゾーンを用意してください。後からメールドメインを追加するには、インストールを見直すことになります。
- プラットフォーム URL は常に確認できる場所に保管してください。共有デプロイプラットフォームを運用する管理者からのコミュニティ報告では、「CLI が間違った URL を指していた」ことが初日の最も一般的な問題として一貫して挙げられています。

## Void Platform: Void への到達方法、ステップバイステップ

以下の順序は意図された順番です。最初にインストールし、次に共有サービスを設定し、その後に開発者を迎え入れます。CLI のステップに先走ることが、プラットフォームが壊れていると結論づける最も一般的な理由です。

### ステップ 1 — コアプラットフォームをインストールする

管理者がプラットフォームをインストールして維持します。開発者はサーバー側に何もインストールしません。コアインストールにはマネージド Sandboxes とメールゲートウェイが含まれますが、多くの人が期待するいくつかの機能 — ユーザーダッシュボード、マネージド GitHub ビルドと webhook、ビルド Containers、カスタムプロジェクトドメイン — は意図的に含まれていません。コアは軽量だと想定してください。

### ステップ 2 — 共有メールドメインとゾーンを設定する

メールゲートウェイはコアインストールに含まれますが、共有メールドメインとゾーンを設定するまで機能しません。これを省略しても、大きなエラーは出ません。単にメールの動作が得られないだけです。オプションの追加機能ではなく、インストールの一部として扱ってください。

### ステップ 3 — ログイン方法を有効にする

サインインは「有効なログイン方法を通じて」行われます。つまり、プラットフォームは管理者が有効にしたものだけを提供します。開発者を招待する前に、少なくとも1つの方法がエンドツーエンドで機能することを確認してください。できれば、プライベートブラウザウィンドウで自分自身でサインインして確認します。

### ステップ 4 — Void CLI をプラットフォーム URL に接続する

各開発者は Void CLI をプラットフォーム URL に向けます。これが日常的な意味での「Void に到達する」瞬間です。CLI がプラットフォームを見つけられるか、見つけられないかのどちらかです。API が Access 保護の背後にある場合、オプションの GitHub サービスを追加するソースビルドのプラットフォームは、保護された API に穴を開けるのではなく、分離された webhook ingress のセットアップに従う必要があることに注意してください。

### ステップ 5 — サインインしてデプロイする

有効な方法でサインインしてからデプロイします。直接 Cloudflare と共有プラットフォームという両方のデプロイ先は同じアプリケーション API を使用するため、直接デプロイで学んだことはそのまま当てはまります。

| ステップ | 担当者 | 結果 |
| --- | --- | --- |
| 1. コアをインストール | 管理者 | プラットフォームが存在し、稼働する |
| 2. メールドメイン/ゾーンを設定 | 管理者 | メールゲートウェイが有効になる |
| 3. ログイン方法を有効化 | 管理者 | 人間が認証できる |
| 4. CLI を接続 | 開発者 | ツールがプラットフォームを見つけられる |
| 5. サインインしてデプロイ | 開発者 | 最初のアプリが公開される |

## 直接 Cloudflare か、共有プラットフォームか？ 適切な経路を選ぶ

誰もがプラットフォームを必要とするわけではありません。純粋に自分のためにアプリをデプロイする場合、指針は明確です。Cloudflare に直接デプロイし、プラットフォームのインストールは完全に省略してください。プラットフォームは、チーム全体で共有アクセスと保持された履歴を求める場合に価値を発揮します。

| 機能 | Cloudflare への直接デプロイ | コアのセルフホストプラットフォーム |
| --- | --- | --- |
| Workers AI とプロバイダーリクエスト | 自分のアカウントとゲートウェイ | インストールのゲートウェイとプロキシ |
| ランタイムログ | ライブの Cloudflare tail | 保持されたプラットフォームログ |
| アプリケーションのロールバック | Worker のバージョン | 保持されたプラットフォームのデプロイ |
| Sandboxes | Workers Paid と Docker が必要 | プラットフォームアカウントで Workers Paid が必要 |
| ユーザーダッシュボードとマネージド GitHub ビルド | 不要 | 標準インストールには含まれない |

パターンは明確です。直接デプロイは即時性をもたらし、プラットフォームは保持と共有アクセスをもたらします。「誰が何を、いつデプロイしたか」に6週間後も答えが必要かどうかで選んでください。

## すぐには手に入らないオプション機能

新しい管理者が繰り返し驚くのは、インストールしたプラットフォームが想像していたプラットフォームではないことです。ここでは正直に分けて説明します。

| 機能 | コアインストールに含まれるか？ | 代わりにどうするか |
| --- | --- | --- |
| マネージド Sandboxes | はい | 何も不要 — デフォルトで利用可能 |
| メールゲートウェイ | はい、設定後 | 共有メールドメインとゾーンを設定する |
| ユーザーダッシュボード | いいえ | CLI 主導のワークフローに頼る |
| GitHub ビルドと webhook | いいえ | ソースビルド経由でオプションサービスを追加する |
| ビルド Containers | いいえ | オプション設定で追加する |
| カスタムプロジェクトドメイン | いいえ | プラットフォーム提供のルーティングを前提に計画する |

ソースビルドを通じて GitHub サービスを追加し、API が Access で保護されている場合は、分離された webhook ingress のガイダンスに従ってください。これは、API 保護を弱めることなく webhook を受け取れるようにするためにまさに存在します。

## トラブルシューティング: Void に到達できないとき

「到達できない」という報告のほとんどは、いくつかの原因に集約されます。設定を変更し始める前に、症状を照合してください。

| 症状 | 考えられる原因 | 最初に試すこと |
| --- | --- | --- |
| CLI がプラットフォームを見つけられない | プラットフォーム URL が間違っている | 管理者が配布した URL を再確認する |
| サインインページに何も表示されない | ログイン方法が有効になっていない | 管理者に有効化を依頼する |
| メール機能がまったく動作しない | 共有メールドメインまたはゾーンが設定されていない | メールドメインとゾーンの設定を完了する |
| Sandboxes が起動しない | プラットフォームアカウントで Workers Paid が有効になっていない | プラットフォームアカウントのプランを確認する |
| ログイン後にダッシュボードがない | コアインストールに含まれていない | 代わりに CLI ワークフローを使用する |
| Webhook が Access の背後でブロックされる | オプションの GitHub サービスを備えた保護された API | 分離された webhook ingress 設定を適用する |

2つの習慣でこれらのほとんどを防げます。CLI を触る前に URL を確認すること、そしてチームをオンボーディングする前にログイン方法が機能することを確認することです。それ以外は、プラットフォームが壊れているというより、設定の詳細であることがほとんどです。

## FAQ

**自分のアプリをデプロイするために Void プラットフォームをインストールする必要はありますか？**
いいえ。自分のためにアプリをデプロイする場合は、Cloudflare に直接デプロイしてください。プラットフォームはチーム共有のための構成要素であり、前提条件ではありません。

**プラットフォームのインストール後、開発者はどうやって Void に到達しますか？**
Void CLI をプラットフォーム URL に接続し、有効なログイン方法でサインインします。管理者の役割は、開発者が試す前に両方が存在することを確認することです。

**私は管理者ではなく開発者です。Void Platform で、自分の側で Void に到達するには実際に何が必要ですか？**
3つです。プラットフォーム URL、有効なログイン方法に紐づいたアカウント、ローカルにインストールされた CLI です。どれかが欠けている場合は、CLI をデバッグするのではなく管理者に尋ねてください。

**なぜ私のプラットフォームはドキュメントが示すより機能が少なく見えるのですか？**
標準インストールは意図的に軽量だからです。ユーザーダッシュボード、マネージド GitHub ビルドと webhook、ビルド Containers、カスタムプロジェクトドメインはオプションの追加機能であり、デフォルトではありません。何かが壊れていると決めつける前に、インストールに実際に何が含まれているかを確認してください。
