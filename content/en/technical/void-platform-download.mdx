## What "Void Platform Download" Really Means

Most people searching for a Void Platform download expect a single installer file and a next-next-finish wizard. The reality is different: Void is a self-hosted platform your team deploys into a shared Cloudflare account, and the "download" step is really about getting the platform tooling in place and running its setup flow. Understanding that distinction up front saves hours, because it decides whether you need a platform at all. If you are shipping an app just for yourself, you deploy directly to Cloudflare and skip the platform entirely.

A Void platform is the shared layer between your developers and Cloudflare. As the administrator, you install it and keep it running. Developers then point the Void CLI at the platform's URL, sign in through one of the enabled login methods, and deploy their apps into that shared account. Every part of the Void Platform download process exists to make that handoff reliable and repeatable.

Because the platform lives in your Cloudflare account rather than on a laptop, the download is less about a file and more about infrastructure. You will be working with Cloudflare credentials, plan requirements, and a documented set of services. The table below sets expectations straight.

| What people expect from a Void Platform download | What actually happens |
| --- | --- |
| A single `.exe` or `.dmg` installer | The platform is built and deployed into your own Cloudflare account |
| Runs on your laptop | Runs in the cloud, shared by the whole team |
| Instant, no account setup | Requires Cloudflare credentials, a Workers Paid plan, and documented infrastructure |
| Mandatory for every project | Solo developers can deploy directly to Cloudflare instead |
| Everything included out of the box | A core install is intentionally lean; add-ons are separate |

## Prerequisites and Credentials Checklist

Before you start a Void Platform download, collect the accounts and access you will need. In practice, most failed installations come from a missing permission or an under-provisioned plan, not from the platform itself. Working through this list first turns a frustrating afternoon into a smooth setup.

| Requirement | Why you need it | Notes |
| --- | --- | --- |
| Cloudflare account | Hosts the platform and every deployed app | Shared by the entire team |
| Workers Paid plan | Required for managed Sandboxes | Applied to the platform account |
| Workers for Platforms | Required for a team platform | Pair with the documented infrastructure |
| Platform credentials | Authenticate installation and API access | Covered in the official installation guides |
| Shared mail domain and zone | Turns on the email gateway | Optional — email stays off until configured |
| Void CLI | How developers connect and deploy | Installed on each developer machine |

Two of these deserve extra attention. First, the Workers Paid plan must be active on the platform account, not just on an individual developer's account, or Sandboxes will not run. Second, credentials should be handled like production secrets from day one, since the installation gateway and proxy sit in front of Workers AI and provider requests for every app on the platform.

If your organization uses Cloudflare Access to protect the API, plan the webhook path early. Platforms built from source that add the optional GitHub services need an isolated webhook ingress so incoming webhooks are not blocked by Access. Retrofitting that later is far more painful than designing for it up front.

## Core Install vs. Optional Services

One of the biggest surprises after a Void Platform download is discovering what a standard installation includes — and what it deliberately leaves out. The core is lean by design: managed Sandboxes plus an email gateway, with email only enabled once you configure a shared mail domain and zone.

| Included in a core installation | Not included in a core installation |
| --- | --- |
| Managed Sandboxes | User dashboard |
| Email gateway (after domain and zone setup) | GitHub builds and webhooks |
| Shared access for the team | Build Containers |
| Retained deployment history | Custom project domains |
| Installation gateway and proxy for AI requests | Managed GitHub integrations of any kind |

That split matters when you plan a rollout. A team that expects a polished dashboard on day one will be disappointed unless someone builds or adds it. Likewise, teams that rely on GitHub-driven builds need the optional services layer, and teams that want branded project domains need to plan that work separately.

The practical approach is to install the core first, verify that Sandboxes and deployments work, and only then layer on the extras. Each add-on increases the surface area you maintain, and a broken optional service is much easier to diagnose when the core is known-good.

## Direct Cloudflare vs. a Self-Hosted Platform

Before committing to a Void Platform download, confirm that a platform is the right target. Both paths use the same application APIs, so you are not locked in either way — the difference is shared access and retained history.

| Feature | Direct to Cloudflare | Core self-hosted platform |
| --- | --- | --- |
| Workers AI and provider requests | Your account and your gateway | Installation gateway and proxy |
| Runtime logs | Live Cloudflare tail | Retained platform logs |
| Application rollback | Worker versions | Retained platform deployments |
| Sandboxes | Requires Workers Paid and Docker | Requires Workers Paid on the platform account |
| User dashboard and managed GitHub builds | Not required | Not included in a standard installation |

The short version: go direct if you are deploying an app for yourself and want the shortest path to production. Choose the platform if your team needs a shared deployment target, retained logs, and the ability to roll back to a specific retained deployment rather than a raw Worker version. Note the Sandboxes difference too — direct deployments need Docker locally, while the platform pushes that requirement to the platform account.

## Step-by-Step: From Void Platform Download to First Deploy

With prerequisites confirmed, the installation itself follows a predictable sequence. Treat each step as a gate: do not move on until the previous one is verified.

| Step | What you do | What "done" looks like |
| --- | --- | --- |
| 1 | Confirm your target: direct Cloudflare or self-hosted platform | A clear decision, documented for the team |
| 2 | Prepare the Cloudflare account, plans, and credentials | Workers Paid active; Workers for Platforms ready for a team setup |
| 3 | Build and deploy the platform using the official installation guide | Platform reachable at its URL |
| 4 | Configure the shared mail domain and zone (optional) | Email gateway active and sending |
| 5 | Add optional services such as GitHub builds or build Containers | Each add-on verified independently |
| 6 | Connect developers through the Void CLI | A developer signs in and ships a test app |

**Step 1 and 2: decide and provision.** Write down whether you are running direct or self-hosted before touching anything. Then provision the Cloudflare account, confirm the Workers Paid plan, and set up Workers for Platforms if the platform is for a team. Keep credentials in a shared secret store rather than passing them around in chat.

**Step 3 and 4: install and configure email.** Follow the official [Void self-hosted platform installation guide](https://void.cloud/guide/self-hosted-platform) rather than improvising, since the documented infrastructure matters. Once the platform is reachable, configure the shared mail domain and zone if you want the email gateway — without that step, email simply stays disabled.

**Step 5 and 6: extend and onboard.** Add optional services one at a time and test after each. Then hand developers the platform URL and CLI instructions, and have one person complete a full sign-in and deploy as a smoke test before announcing the platform to the wider team.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Sandboxes will not start | Workers Paid not active on the platform account | Verify or upgrade the plan on that account |
| Developers cannot sign in | No login method enabled | Enable a supported login method in the platform configuration |
| Email never sends | Shared mail domain or zone missing | Configure the domain and zone, then retest |
| GitHub webhooks fail behind Access | Webhook ingress not isolated | Follow the isolated webhook ingress setup |
| Team features unavailable | Workers for Platforms not configured | Complete the documented infrastructure |

## Frequently Asked Questions

**Is there a Void Platform download for Windows or macOS?**
No — there is no consumer desktop installer. A Void Platform download means building and deploying the platform into your own Cloudflare account. Your local machine only needs the Void CLI so developers can connect to the platform URL and deploy.

**Do I need a Void Platform download if I am a solo developer?**
Usually not. If you are deploying an app for yourself, deploy directly to Cloudflare and skip the platform. The platform earns its keep when a team needs a shared deployment target, retained logs, and retained deployment history for rollbacks.

**What is missing from a standard installation?**
The user dashboard, GitHub builds and webhooks, build Containers, and custom project domains are all outside the core install. Managed Sandboxes and the email gateway are included, though email only works once a shared mail domain and zone are configured.

**What plan does a team platform require?**
A team platform requires Workers for Platforms plus the documented infrastructure, and managed Sandboxes require a Workers Paid plan on the platform account. Exact features depend on how your installation is configured, so review the official guides before you start.
