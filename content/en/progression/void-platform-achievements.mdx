A self-hosted Void platform looks like a single installation and behaves like a progression system. Most teams celebrate the first successful deploy, then discover that the meaningful Void Platform achievements come in waves — core services first, shared access next, and optional build tooling last. This guide maps those Void Platform achievements into a trackable checklist so administrators know exactly what to unlock next and developers know what to expect from the platform they are signing into.

## What Void Platform Achievements Actually Track

There is no trophy screen inside a Void platform. The progression here is capability-based: each milestone represents a new thing your team can do that it could not do before. That framing matters because it stops administrators from treating installation as a single checkbox and starts them treating it as a sequence of unlocks, each with its own prerequisites.

The milestones below form the backbone of any Void Platform achievements list. Later tiers assume earlier ones are already stable, which is why skipping ahead usually produces confusing errors rather than faster progress.

| Tier | Achievement | What it proves | How you verify it |
| --- | --- | --- | --- |
| 1 | Platform reachable | The platform URL responds and a login method is enabled | A developer connects the Void CLI and signs in |
| 2 | First deployment | Apps land in the shared Cloudflare account | The deployment appears in retained platform history |
| 3 | Shared access | More than one developer can ship independently | Multiple team members deploy to the same platform URL |
| 4 | Retained history | Rollback is available beyond raw Worker versions | Previous deployments can be restored from the platform |
| 5 | Email gateway live | A shared mail domain and zone are configured | Mail flows through the platform gateway |
| 6 | Optional services | GitHub builds, webhooks, containers, or custom domains added | The feature responds on a source-built platform |

### Why the order matters

Sandboxes, for example, require Workers Paid on the platform account. If a team installs first and only later discovers the billing prerequisite, the "achievement" stalls at tier one while everyone assumes something is broken. Reading the prerequisite list before installing is the cheapest progression shortcut available.

## The Core Installation Milestones

A core installation is deliberately small. It ships managed Sandboxes and an email gateway, and email only becomes active once you configure a shared mail domain and zone. Everything else that people associate with a polished developer platform — the user dashboard, GitHub builds and webhooks, build Containers, and custom project domains — sits outside the core install.

That is not a limitation so much as a design choice: the core gives you shared access and retained deployment history, and optional services are layered on top by administrators who need them.

| Step | Task | Achievement unlocked | Difficulty |
| --- | --- | --- | --- |
| 1 | Review prerequisites | You know what infrastructure and billing the install needs | Low |
| 2 | Prepare credentials | The installer can authenticate against your Cloudflare account | Low |
| 3 | Run the core installation | Sandboxes and the email gateway are provisioned | Medium |
| 4 | Enable a login method | Developers can authenticate through a supported provider | Low |
| 5 | Point the Void CLI at the platform URL | The platform is reachable from developer machines | Low |
| 6 | Deploy a first app | Shared deployment flow is proven end to end | Medium |
| 7 | Configure a shared mail domain and zone | The email gateway switches on | Medium |

Following the [official Void self-hosted platform installation guide](https://void.cloud/guide/self-hosted-platform) during steps 1 through 3 keeps you aligned with the current prerequisite list rather than a blog post written months earlier.

### A note on solo deployments

If you are deploying an app only for yourself, you do not need a platform at all — deploying directly to Cloudflare is the shorter path. The Void Platform achievements described here are team achievements, and they only pay off once more than one person is shipping code.

## Optional Services and the Advanced Void Platform Achievements

Once the core is stable, the advanced tier opens up. These are the features that turn a shared deployment target into something closer to an internal product: a user dashboard, managed GitHub builds, webhook-driven deploys, build Containers, and custom project domains per project.

| Optional service | Included in a standard install? | What it unlocks | Watch out for |
| --- | --- | --- | --- |
| User dashboard | No | Self-service visibility for developers | Needs its own hosting and auth wiring |
| GitHub builds and webhooks | No | Deploys triggered from repository events | Use isolated webhook ingress when Access protects the API |
| Build Containers | No | Custom build environments | Extra infrastructure to maintain |
| Custom project domains | No | Branded URLs per app | DNS and zone configuration per project |

That webhook detail is the one administrators most often miss. Source-built platforms that add the optional GitHub services should follow an isolated webhook ingress setup when Cloudflare Access protects the API — otherwise GitHub's callbacks hit an authentication wall and deploys silently stop firing.

| Advanced achievement | Prerequisite | Effort | Payoff |
| --- | --- | --- | --- |
| GitHub-triggered deploys | Core install plus optional GitHub services | High | Push-to-deploy workflow |
| Isolated webhook ingress | Access protecting the API | Medium | Reliable webhook delivery |
| Custom project domains | Per-project DNS access | Medium | Clean, memorable app URLs |
| Build Containers | Workers Paid on the platform account | High | Reproducible build environments |

## Direct Cloudflare vs. a Self-Hosted Platform

A common source of confusion is that both targets use the same application APIs. The difference is not what an app can call — it is what the surrounding platform remembers and shares. Understanding this table prevents teams from chasing Void Platform achievements they do not actually need.

| Feature | Direct Cloudflare | Core self-hosted platform |
| --- | --- | --- |
| Workers AI and provider requests | Your own account and gateway | Installation gateway and proxy |
| Runtime logs | Live Cloudflare tail | Retained platform logs |
| Application rollback | Worker versions | Retained platform deployments |
| Sandboxes | Requires Workers Paid and Docker | Requires Workers Paid on the platform account |
| User dashboard and managed GitHub builds | Not required | Not included in a standard installation |

The pattern is consistent: direct deployment gives you immediacy, while the platform gives you retention and shared access. Teams that mostly need live debugging may find the direct path sufficient. Teams that need history, rollback, and multiple developers on one URL should treat the platform as the target.

## A Step-by-Step Progression Plan

Treat the rollout like a game with six levels. Finish a level, verify it, document it, and only then start the next one. The table below is a practical sequence that mirrors how most administrators actually work through Void Platform achievements.

| Phase | Focus | Typical blocker | Achievement unlocked |
| --- | --- | --- | --- |
| 1 | Prerequisites and credentials | Missing Workers Paid plan or account access | Ready to install |
| 2 | Core installation | Unclear infrastructure requirements | Sandboxes and gateway provisioned |
| 3 | Authentication | No login method enabled | Developers can sign in |
| 4 | First deploy | CLI pointed at the wrong URL | Shared deployment proven |
| 5 | Email gateway | Shared mail domain and zone not configured | Platform email active |
| 6 | Optional services | Webhook ingress blocked by Access | GitHub builds and custom domains |

A few practical tips that shorten each phase:

- Write down the platform URL in your team docs the moment it exists; half of all "the CLI is broken" reports are stale URLs.
- Confirm billing prerequisites before installing, not after. Sandboxes are the usual casualty.
- Test rollback with a throwaway app before you need it in an incident.
- Keep optional services off until the core is boringly stable.
- Re-read the prerequisites whenever you upgrade infrastructure, since configuration determines which features are even available.

## Tracking Void Platform Achievements Across a Team

Player experience suggests that the hardest part of a platform rollout is not the install — it is keeping everyone aligned on what the platform currently supports. A shared checklist fixes that. Put your Void Platform achievements list in the same repository your team already reads, and mark each tier as complete only when someone other than the administrator has verified it.

A lightweight tracking approach works well:

- One owner per phase, usually the administrator for tiers 1–2 and a senior developer for tiers 3–6.
- A dated note for each completed milestone so future maintainers know when a capability appeared.
- A short "not included in core" section listing the dashboard, GitHub builds, build Containers, and custom domains, so nobody assumes they exist by default.
- A recurring review of retained logs and deployment history, which are the two capabilities that justify the platform in the first place.

Community reports also point out that team platforms carry a heavier infrastructure requirement than a personal install. A team platform requires Workers for Platforms and the documented supporting infrastructure, and features depend entirely on how the installation is configured — so the same checklist can produce different results on two different platforms.

## FAQ

**Do Void Platform achievements exist as an in-product feature?**
No. There is no achievement system inside the platform itself. The term is used here to describe progression milestones — install, shared access, retained history, email, and optional services — that an administrator unlocks in sequence.

**How many milestones are in a typical Void Platform achievements checklist?**
The core track has roughly five to seven verifiable steps depending on how granular you get, and the optional tier adds another four for GitHub builds, webhook ingress, build Containers, and custom project domains.

**Can I unlock the advanced Void Platform achievements without a core install?**
Not practically. Optional services are layered on top of a working core platform. If you only need to deploy an app for yourself, skip the platform entirely and deploy directly to Cloudflare.

**Why does the email gateway stay inactive after installation?**
Email is only enabled once you configure a shared mail domain and zone. Until that configuration exists, the gateway is installed but not serving — a milestone that looks complete but is not.
