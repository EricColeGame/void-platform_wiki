## What a Void Platform Actually Is

Standing up shared deployment infrastructure for a team usually sounds like a week of plumbing work, but a Void Platform compresses that into a guided installation. Instead of every developer wiring up their own Cloudflare account, you install once and give the whole team a single place to ship apps, with retained logs and rollback history. This Void Platform beginner guide walks through what the platform is, what you need before you start, and how to get your first developer deploying without guesswork.

The core idea is simple: a Void platform is a shared deployment target that lives inside one Cloudflare account. An administrator installs and maintains it. Developers then connect the Void CLI to the platform's URL, sign in through whichever login method is enabled, and deploy their apps. The platform handles the shared plumbing so nobody re-solves authentication, routing, and release history on every project.

There is one important caveat that saves beginners hours: if you're deploying an app only for yourself, you don't need a platform at all. Deploy directly to Cloudflare. A Void Platform earns its keep when multiple people share infrastructure and need consistent access plus a record of what shipped.

### When a shared platform is worth it

- Two or more developers deploying to the same Cloudflare account
- A need for retained deployment history rather than live-only logs
- Rollbacks that should be a platform action, not a manual Worker version hunt
- Centralized control over which login methods are allowed

## Direct Cloudflare vs. a Core Self-Hosted Void Platform

Both targets use the same application APIs, which means an app that runs on one generally runs on the other. The difference is what surrounds the app: shared access, retained history, and a gateway that proxies provider requests. The table below paraphrases the official comparison.

| Feature | Direct to Cloudflare | Core self-hosted Void Platform |
| --- | --- | --- |
| Workers AI and provider requests | Your own account and gateway | Installation gateway and proxy |
| Runtime logs | Live Cloudflare tail | Retained platform logs |
| Application rollback | Worker versions | Retained platform deployments |
| Sandboxes | Requires Workers Paid plus Docker | Requires Workers Paid on the platform account |
| User dashboard and managed GitHub builds | Not required | Not included in a standard install |

The practical takeaway for anyone reading a Void Platform beginner guide for the first time: start direct if you're solo, and move to a platform the moment coordination becomes the bottleneck. Migrating later is far less painful than maintaining infrastructure you don't need yet.

## Prerequisites: What to Line Up Before You Install

Most failed first installs aren't technical failures — they're missing prerequisites. The official installation docs split this into prerequisites and credentials, and it's worth treating both as a checklist rather than a skim.

| Requirement | Why it matters | Beginner note |
| --- | --- | --- |
| A Cloudflare account dedicated to the platform | All shared deployments land here | Avoid mixing personal projects into it |
| Workers Paid on the platform account | Sandboxes won't run without it | Confirm the plan before installing |
| Workers for Platforms | Required for a true team platform | Only needed for multi-tenant setups |
| A domain and zone for email | The email gateway activates only when configured | Skip it and email stays off |
| Void CLI on developer machines | The primary way developers deploy | Install before onboarding day |
| Admin credentials for the install | Needed to bootstrap and maintain the platform | Store them somewhere shared and auditable |

### The prerequisite most people miss

Email is the classic tripwire. A core installation includes an email gateway, but it only switches on once you configure a shared mail domain and zone. Teams install, test, and then wonder why mail never arrives. Decide up front whether you need email, and if you do, have the domain ready on day one.

## Installing a Void Platform in the Right Order

Order matters more than speed. The sequence below follows the structure of the official guides and keeps you from configuring features that depend on something you haven't built yet.

| Step | What you do | Why it comes here |
| --- | --- | --- |
| 1 | Read the prerequisites page fully | Prevents mid-install surprises |
| 2 | Gather and store credentials | The install needs them immediately |
| 3 | Decide core-only or extended scope | Changes what you configure later |
| 4 | Run the core installation | Delivers Sandboxes and the email gateway |
| 5 | Configure the shared mail domain and zone | Turns the email gateway on |
| 6 | Verify admin access to the platform | Confirms you can maintain it |
| 7 | Connect the Void CLI to the platform URL | The developer entry point |
| 8 | Sign in with an enabled login method | Proves authentication works end to end |
| 9 | Deploy a throwaway test app | Validates the full path before onboarding |

Steps 7 through 9 are the ones beginners rush. A five-minute smoke test — one tiny app, deployed and then rolled back — catches configuration problems while the context is still fresh. If you follow the [official Void self-hosted platform installation guide](https://void.cloud/guide/self-hosted-platform), keep it open beside this Void Platform beginner guide and work top to bottom.

## What Ships in the Core Install — and What Doesn't

A standard installation is deliberately lean. Knowing the boundary saves you from hunting for menus that were never built.

| Included in a core install | Not part of a standard install |
| --- | --- |
| Managed Sandboxes | User dashboard |
| Email gateway (once a mail domain and zone are set) | Managed GitHub builds and webhooks |
| Shared access for the team | Build Containers |
| Retained deployment history and logs | Custom project domains |

If you need the missing pieces, they're added through optional services — most commonly on source-built platforms. One caution from the docs: if you add the optional GitHub services to a source-built platform and Cloudflare Access protects the API, use the isolated webhook ingress setup. Otherwise webhook traffic and Access policies collide, and builds fail in ways that look mysterious.

Community reports from teams running shared platforms tend to agree on one thing: add optional services one at a time, and deploy a test app after each addition. Stacking three new services before testing turns a simple misconfiguration into a long debugging session.

## Onboarding Developers Without the Usual Friction

The administrator's job doesn't end at install. Developers need three things: the platform URL, an enabled login method, and a working CLI.

- **Share the platform URL explicitly.** Not a bookmark, not a Slack message from three months ago — put it in your team docs.
- **Confirm which login methods are enabled** before telling anyone to sign in, so nobody stalls on a method you never turned on.
- **Standardize CLI setup.** A one-page internal note covering install, connect, and sign-in beats answering the same question five times.
- **Set a deployment convention.** Even a lightweight rule about naming and rollback expectations pays off once history accumulates.

Paragraph under 120 words — good. Also worth noting: because a team platform depends on Workers for Platforms and the documented infrastructure, features vary by configuration. Don't assume your platform behaves like a tutorial's; check what your own installation actually enables.

## Beginner Mistakes That Waste the Most Time

| Mistake | What it looks like | The fix |
| --- | --- | --- |
| Installing a platform for a solo project | Extra infrastructure with no benefit | Deploy directly to Cloudflare instead |
| Expecting a dashboard | Searching for a UI that isn't installed | Plan the optional services or work CLI-first |
| Missing Workers Paid on the platform account | Sandboxes refuse to run | Verify the plan on the right account |
| Enabling email without a domain and zone | Mail silently never sends | Configure the shared mail domain first |
| Skipping the test deployment | Problems surface during onboarding | Deploy and roll back one throwaway app |

The pattern behind all five is the same: assumptions about what "installed" means. A Void Platform beginner guide can only take you so far — the rest is verifying your specific configuration rather than trusting a general description.

## FAQ

**Do I need a Void Platform to deploy an app?**
No. If you're deploying for yourself, deploy directly to Cloudflare and skip the platform entirely. A Void Platform is for teams that want shared access and retained deployment history.

**How long does a first install take?**
That depends on how much of the prerequisite list you've already handled. Teams that gather credentials and confirm their Cloudflare plan in advance move through the core installation quickly; teams that discover a missing requirement midway often restart.

**What's missing from a standard installation?**
The user dashboard, managed GitHub builds and webhooks, build Containers, and custom project domains are all outside the core install. Sandboxes and the email gateway are included, though email only activates once you configure a shared mail domain and zone.

**Can developers roll back a bad deployment?**
Yes. On a core self-hosted platform, rollback uses retained platform deployments rather than raw Worker versions, which is one of the main reasons teams adopt a Void Platform beginner guide approach instead of ad-hoc direct deployments.

**Where should a beginner start?**
Read the prerequisites and credentials pages, confirm your plan and account setup, then install the core and validate with one small app. Everything else can be layered on afterward.
