Setting up shared deployment infrastructure is easy to postpone — until three developers are each shipping to their own Cloudflare account and nobody can roll back the same release. A Void Platform walkthrough fixes that by turning a vague "we should self-host" ambition into an ordered checklist. Below you'll find a practical Void Platform walkthrough that covers what the platform actually is, which credentials to gather first, how the core install is sequenced, and which optional services most teams bolt on later.

Most confusion around this product comes from a single fork in the road: deploying for yourself versus deploying for a team. If you're shipping your own app, you deploy directly to Cloudflare and never touch a platform install. If you're the administrator standing up shared infrastructure, the platform becomes the thing you install, maintain, and hand a URL to. Everything here assumes you're in that second camp.

## What a Void Platform Actually Does

A Void platform lets a team deploy applications into a shared Cloudflare account. That one sentence carries most of the value: instead of every developer wiring up their own account, tokens, and gateway, the administrator installs and maintains one platform. Developers then point the Void CLI at its URL, sign in through an enabled login method, and deploy.

The platform isn't a separate hosting product. Both deployment targets use the same application APIs, so an app doesn't need to be rewritten to move from a direct Cloudflare deploy onto a team platform. What the platform adds is shared access plus retained deployment history — two things that matter enormously once more than one person ships code.

| Role | What they own | Where they work |
| --- | --- | --- |
| Administrator | Installing and maintaining the platform, enabling login methods, configuring the shared mail domain | Cloudflare account + platform URL |
| Developer | Connecting the Void CLI, signing in, deploying apps | Void CLI → platform URL |
| Solo builder | Shipping a single app with no platform at all | Their own Cloudflare account |

The split matters because it defines your job. During installation you are the administrator, not a developer. Your success metric isn't "my app is live" — it's "a teammate I've never met can authenticate and deploy without messaging me."

## Prerequisites and Credentials to Line Up First

The fastest way to stall a Void Platform walkthrough is to discover halfway through that you're missing a plan tier or an account permission. The official [Void self-hosted platform installation guide](https://void.cloud/guide/self-hosted-platform) splits this into prerequisites and credentials for good reason: they're separate decisions with separate owners.

Work through the list below before you touch the installer. Each row is something you should be able to answer with a name, not a shrug.

| Prerequisite | Why it matters | Decide before install? |
| --- | --- | --- |
| Dedicated Cloudflare account for the platform | Every team app deploys into this one shared account | Yes — never a personal account |
| Workers Paid on the platform account | Required for managed Sandboxes | Yes |
| Workers for Platforms + documented infrastructure | Required for a team platform | Yes |
| At least one login method | Developers can only sign in through an enabled method | Yes |
| Shared mail domain and zone | Email stays disabled until both are configured | Only if you want email |
| Credentials and API access | Needed to install and to maintain over time | Yes |

Two of these are commonly underestimated. The first is the account choice: migrating a platform later is far more painful than choosing a dedicated account up front. The second is the login method — it is not a post-install afterthought, it is the gate every developer passes through.

## The Void Platform Walkthrough, Step by Step

The sequence below follows the installation guides in order, from prerequisites through credentials and into the core install. Treat each step as a gate: don't advance until the "done" column is genuinely true.

| # | Step | What "done" looks like |
| --- | --- | --- |
| 1 | Decide direct deploy vs. shared platform | You've confirmed you actually need a platform |
| 2 | Complete prerequisites | Account, plan tier, and infrastructure confirmed |
| 3 | Gather credentials | Install and maintenance access in hand |
| 4 | Install the core platform | Managed Sandboxes and email gateway present |
| 5 | Configure the shared mail domain and zone | Email gateway active (optional but recommended) |
| 6 | Enable a login method | Developers can authenticate successfully |
| 7 | Connect the Void CLI to the platform URL | A first test deploy succeeds end to end |
| 8 | Plan optional services | A written list of what you're adding later |

### Steps 1–3: Scope, prerequisites, credentials

Start by writing down the answer to a blunt question: is this platform for one person or for a team? If it's one person, stop — deploy directly to Cloudflare instead. If it's a team, the answer commits you to Workers for Platforms and the documented infrastructure, so budget for that before scheduling any install window.

### Steps 4–5: Install the core and switch on email

The core installation includes managed Sandboxes and an email gateway. Email doesn't come online by itself; it's enabled when you configure a shared mail domain and zone. If transactional email from deployed apps is part of your plan, treat this as a required step rather than a nice-to-have, and verify it with a real send before you invite developers.

### Steps 6–8: Authentication, first deploy, and the roadmap

Enable a login method, hand the platform URL to one pilot developer, and have them connect the Void CLI and deploy something small. That single test surfaces more configuration problems than any checklist. Once it passes, write down the optional services you're deferring — GitHub builds, build Containers, custom project domains — so nobody assumes they shipped with the core.

## Direct Cloudflare vs. the Core Self-Hosted Platform

This is the comparison table worth bookmarking, because it answers "what am I actually gaining?" Both targets share the same application APIs; the differences are about shared access, retention, and where requests flow.

| Feature | Direct Cloudflare | Core self-hosted platform |
| --- | --- | --- |
| Workers AI and provider requests | Your account and gateway | Installation gateway and proxy |
| Runtime logs | Live Cloudflare tail | Retained platform logs |
| Application rollback | Worker versions | Retained platform deployments |
| Sandboxes | Requires Workers Paid and Docker | Requires Workers Paid on the platform account |
| User dashboard and managed GitHub builds | Not required | Not included in a standard installation |

Read the last two rows carefully. Sandboxes on the platform only need Workers Paid on the platform account, whereas direct deployment also expects Docker in your local workflow. And the dashboard plus managed GitHub builds are not part of a standard installation on either side — they're additions you opt into.

For a solo project, the left column is less work for the same application APIs. For a team, the right column's retained logs and retained deployments are what make debugging a shared release possible at all.

## Optional Services and Configuration Traps

Once your Void Platform walkthrough clears the core install, the remaining work is elective — but each option has a configuration consequence. Plan them deliberately rather than discovering them when a developer asks why their branch preview is missing.

| Capability | In the core install? | What to know |
| --- | --- | --- |
| Managed Sandboxes | Yes | Core feature |
| Email gateway | Yes, once mail domain and zone are set | Off by default until configured |
| User dashboard | No | Optional addition |
| GitHub builds and webhooks | No | Optional; source-built platforms adding them should use the isolated webhook ingress setup when Access protects the API |
| Build Containers | No | Optional addition |
| Custom project domains | No | Optional addition |

| Symptom | Likely cause | Where to look |
| --- | --- | --- |
| A developer can't sign in | No login method enabled | Platform login configuration |
| Email never arrives | Shared mail domain and zone not configured | Email gateway setup |
| Webhook deliveries fail behind Access | Ingress not isolated | Isolated webhook ingress setup |
| No rollback history for a release | Deploying direct, not through the platform | Deployment target choice |
| Feature you expected is missing | It's an optional service, not core | Your deferred-services list |

Two habits prevent most of these. First, keep a short configuration record: which login methods are enabled, which mail domain is shared, and which optional services are live. Second, when Cloudflare Access protects the API and you're running a source-built platform with GitHub services, follow the isolated webhook ingress setup rather than loosening Access — the fix belongs in the ingress path, not in your security posture.

Finally, remember that a team platform depends on its configuration. Features documented for one installation may be absent from yours simply because they weren't enabled, so verify against your own setup instead of assuming a default.

## FAQ

**Do I need a Void Platform walkthrough if I'm only deploying my own app?**
No. If you're deploying an app for yourself, deploy directly to Cloudflare. Installing a platform is only worth the overhead when a team needs shared access and retained deployment history.

**Is the user dashboard included in a standard installation?**
No. The user dashboard, managed GitHub builds and webhooks, build Containers, and custom project domains are not part of the core installation. Plan for them as separate additions.

**What does the platform account need in order to run Sandboxes?**
Workers Paid on the platform account. Direct Cloudflare deployment has a slightly different requirement and also expects Docker for Sandboxes.

**Can we add GitHub builds after the core install?**
Yes — it's an optional service. If you're on a source-built platform and Cloudflare Access protects the API, set up isolated webhook ingress so builds and webhooks keep working without weakening access control.
